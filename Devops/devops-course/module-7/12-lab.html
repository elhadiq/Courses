Lab: full observability stack

Goal Instrument the app, deploy Prometheus and Grafana into the Module 6 cluster, build a golden-signals dashboard, then trigger an alert by breaking the app on purpose.

Step 1 — instrument and rebuild

cd ~/devops/urlshort
# add prometheus-client to requirements.txt and the code from 6.5 to app/main.py

docker build -t urlshort:0.3.0 .
kind load docker-image urlshort:0.3.0 --name devops
kubectl set image deployment/urlshort-api api=urlshort:0.3.0
kubectl rollout status deployment/urlshort-api

kubectl port-forward svc/urlshort-api 8080:80 &
curl -s localhost:8080/metrics | head -20

Step 2 — install the monitoring stack

curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

kubectl create namespace monitoring

helm install kps prometheus-community/kube-prometheus-stack \
  -n monitoring \
  --set grafana.service.type=NodePort \
  --set grafana.service.nodePort=30300 \
  --set grafana.adminPassword=admin \
  --wait

kubectl get pods -n monitoring

Step 3 — tell Prometheus to scrape your app

The stack installs the Prometheus Operator, so you declare scraping with a custom resource. k8s/servicemonitor.yaml:

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: urlshort-api
  labels:
    release: kps          # must match the helm release, or it is ignored
spec:
  selector:
    matchLabels: { app: urlshort, component: api }
  endpoints:
    - port: http
      path: /metrics
      interval: 15s

Two things must already be true of the Service, both of which you set in Module 6: its metadata carries the labels app: urlshort, component: api (that is what selector.matchLabels above matches — it selects the Service, not the pods), and its port is named http. Confirm, then apply:

kubectl get svc urlshort-api -o jsonpath='{.metadata.labels}{"\n"}{.spec.ports}{"\n"}'

# if the port has no name, add it:
kubectl patch svc urlshort-api --type=json \
  -p='[{"op":"add","path":"/spec/ports/0/name","value":"http"}]'

kubectl apply -f k8s/servicemonitor.yaml

Step 4 — verify the target is up

kubectl port-forward -n monitoring svc/kps-kube-prometheus-stack-prometheus 9090:9090 &
# open http://localhost:9090/targets — urlshort-api should be UP
If the target does not appear Three causes, in order of likelihood: (1) the ServiceMonitor's release label does not match the Helm release name; (2) the Service port has no name; (3) the matchLabels selector does not match the Service's labels. Check with kubectl get servicemonitor -o yaml and kubectl get svc urlshort-api -o yaml.

Step 5 — generate traffic

kubectl port-forward svc/urlshort-api 8080:80 &

# steady successful traffic
for i in $(seq 1 300); do
  curl -s -o /dev/null -X POST localhost:8080/shorten \
    -H 'content-type: application/json' -d '{"url":"https://example.com"}'
  curl -s -o /dev/null localhost:8080/health
  sleep 0.2
done &

# and some 404s for contrast
for i in $(seq 1 60); do curl -s -o /dev/null localhost:8080/r/nothere; sleep 0.5; done &

Step 8 — an alert rule

k8s/alerts.yaml:

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: urlshort-alerts
  labels: { release: kps }
spec:
  groups:
    - name: urlshort
      rules:
        - alert: UrlshortDown
          expr: up{job="urlshort-api"} == 0
          for: 1m
          labels: { severity: page }
          annotations:
            summary: "urlshort-api target is down"

        - alert: UrlshortHighErrorRate
          expr: |
            sum(rate(http_requests_total{status=~"5.."}[2m]))
              / sum(rate(http_requests_total[2m])) > 0.05
          for: 2m
          labels: { severity: page }
          annotations:
            summary: "5xx rate above 5%"
kubectl apply -f k8s/alerts.yaml
# http://localhost:9090/alerts — both should be listed as Inactive

Step 9 — break it and watch the alert fire

# delete Redis: /health now returns 503, and 5xx rate spikes
kubectl scale deployment urlshort-redis --replicas=0

# keep traffic flowing
for i in $(seq 1 200); do curl -s -o /dev/null localhost:8080/health; sleep 0.3; done &

# watch: Inactive -> Pending (for: 2m) -> Firing
# http://localhost:9090/alerts

Now observe what Kubernetes does simultaneously: readiness probes fail, pods leave the Service endpoints — but they are not restarted, because liveness is a separate concern.

kubectl get pods -l component=api
# READY 0/3, STATUS Running, RESTARTS 0  ← exactly right
kubectl get endpoints urlshort-api
# restore
kubectl scale deployment urlshort-redis --replicas=1
kubectl get pods -l app=urlshort -w
# pods become Ready again on their own; the alert resolves
What that exercise demonstrated One dependency failure produced three coordinated behaviours you built across three modules: Kubernetes removed unhealthy pods from rotation without restarting them (Module 6), the app kept reporting accurate metrics throughout (Module 7), and recovery required no human action. That is what the whole course has been assembling.

Step 10 — commit and tidy up

git add k8s grafana requirements.txt app/main.py
git commit -m "feat: prometheus metrics, dashboard and alert rules"
git push

# when finished
kind delete cluster --name devops
