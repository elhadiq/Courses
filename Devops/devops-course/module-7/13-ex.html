Exercise 1 — a business metric

Add a counter for successful redirects, labelled by whether the code was found. Then chart the miss rate.

Solution 
REDIRECTS = Counter("urlshort_redirects_total", "Redirect attempts", ["result"])

# in follow():
if not url:
    REDIRECTS.labels("miss").inc()
    raise HTTPException(status_code=404, detail="unknown code")
REDIRECTS.labels("hit").inc()
sum(rate(urlshort_redirects_total{result="miss"}[5m]))
  / sum(rate(urlshort_redirects_total[5m]))

Note the label has exactly two values. That is what makes it safe — result="hit"|"miss" is bounded, whereas labelling by the code itself would be unbounded.

Exercise 2 — predictive disk alert

Alert when a disk will fill within four hours, rather than at a fixed percentage.

Solution 
- alert: DiskWillFillIn4Hours
  expr: |
    predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4*3600) < 0
  for: 15m
  labels: { severity: page }

predict_linear extrapolates the trend of the last 6 hours forward 4 hours. This is strictly better than a static threshold: a disk sitting stably at 85% never pages anyone, while one climbing fast from 40% does — which matches what actually requires action.

Exercise 3 — find the cardinality bomb

What is wrong, and what breaks?

REQUESTS = Counter("http_requests_total", "...",
                   ["method", "path", "user_id", "status"])
REQUESTS.labels(request.method, request.url.path, user_id, status).inc()
Solution

user_id is unbounded — one series per user. request.url.path is also unbounded here because /r/{code} expands to a distinct path per short link. With 100k users and 1M links the series count is astronomical; Prometheus exhausts memory and is OOM-killed, taking your monitoring down at the exact moment you need it.

Fix: use the templated route, drop user_id entirely. Per-user detail belongs in logs or traces, which are designed for high cardinality.

Exercise 4 — an SLO with a burn-rate alert

Define a 99% availability SLO over 30 days and alert on fast budget burn.

Solution 
# burning 14.4x the sustainable rate exhausts a 30d budget in ~2 days
- alert: ErrorBudgetBurnFast
  expr: |
    (
      sum(rate(http_requests_total{status=~"5.."}[1h]))
        / sum(rate(http_requests_total[1h]))
    ) > (14.4 * 0.01)
  for: 5m
  labels: { severity: page }

Burn-rate alerting is better than a fixed error-rate threshold because it scales with your actual objective: a brief spike that consumes a negligible slice of budget does not page, while a sustained elevation that will blow the month's budget does.
