Exercises

Exercise 1 — matrix builds

Run the test job against Python 3.11 and 3.12 simultaneously.

Solution 
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python: ["3.11", "3.12"]
    steps:
      - uses: actions/setup-python@v5
        with: { python-version: "${{ matrix.python }}" }

fail-fast: false matters: the default cancels all remaining matrix jobs on the first failure, which hides whether the problem is version-specific.

Exercise 2 — scheduled dependency scan

Scan the published image for CVEs every Monday at 06:00 UTC and fail on HIGH or CRITICAL.

Solution 
on:
  schedule:
    - cron: "0 6 * * 1"
  workflow_dispatch:

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: aquasecurity/trivy-action@0.24.0
        with:
          image-ref: ghcr.io/${{ github.repository }}:latest
          severity: "HIGH,CRITICAL"
          exit-code: "1"

This runs on a schedule rather than on push because new CVEs are published against code you have not touched. An image that was clean at build time is not clean forever.

Exercise 3 — a reusable composite action

Three jobs repeat checkout + setup-python + install. Factor that out.

Solution

.github/actions/setup/action.yml:

name: Setup Python env
runs:
  using: composite
  steps:
    - uses: actions/setup-python@v5
      with: { python-version: "3.12", cache: pip }
    - shell: bash
      run: pip install -r requirements.txt

Then in each job: - uses: ./.github/actions/setup (after checkout, since a local action must be on disk first).

Exercise 4 — read a pipeline critically

What is dangerous here?

on: [pull_request_target]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { ref: "${{ github.event.pull_request.head.sha }}" }
      - run: make deploy
        env: { AWS_KEY: "${{ secrets.AWS_KEY }}" }
Solution

pull_request_target runs with full repository secrets, and this workflow explicitly checks out the pull request's code. Anyone in the world can open a PR that changes the deploy target in the Makefile and have your CI run it with production credentials. It also deploys straight from an unreviewed PR with no gate. Use pull_request, deploy only from main, and scope the token.
