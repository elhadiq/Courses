4.4 Services: a real Redis for your tests

You have two options, and the choice is a genuine engineering decision rather than a detail.

Option A — mock Redis

Fast, no infrastructure, but you are testing against a fake. Bugs in how you actually use Redis (expiry semantics, connection loss, pipelining) go undetected.

Option B — a service container

Actions can start real containers alongside the job. Slower by seconds, but you test the real thing. For an app whose entire behaviour depends on Redis, this is the right call:

jobs:
  test:
    runs-on: ubuntu-latest

    services:
      redis:
        image: redis:7-alpine
        ports: ["6379:6379"]
        options: >-
          --health-cmd "redis-cli ping"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 5

    env:
      REDIS_URL: redis://localhost:6379/0

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12", cache: pip }
      - run: pip install -r requirements.txt
      - run: python -m pytest -q
Here localhost is correct Opposite of Module 3. Service containers have their ports published onto the runner's network, and your test process runs directly on the runner — not in a container. So localhost:6379 reaches Redis. If you instead run your tests inside a container, you would use the service name. The rule underneath both cases is the same: address things by where the client is running — which network namespace the process making the call sits in (Module 2.7).
