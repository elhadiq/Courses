Networking Basics

Almost every "it works locally but not in production" bug is a networking bug. This module gives you the model — addresses, ports, names, protocols, firewalls — that makes the next four modules make sense instead of feeling like magic incantations.

2.1 Why this module comes before Docker

In the next four modules you will hit all of these:

  • -p 8080:80 — which side is the host? (Module 3)
  • redis://redis:6379/0 works but redis://localhost:6379 does not. (Module 3)
  • A CI service container reached at localhost, the opposite of the above. (Module 4)
  • A Kubernetes Service with a ClusterIP, a targetPort, and a name that resolves to urlshort-api.default.svc.cluster.local. (Module 6)
  • A security group that lets 443 in but not 6379.

Every one of those is the same handful of ideas wearing different clothes. Learn the ideas once here and those five items stop being things you memorise.

Why it exists Networking is the substrate everything else runs on. Containers do not invent new networking — they use Linux network namespaces, which is why a container's localhost behaves exactly like a separate machine's localhost. Once you know that, the container behaviour is obvious rather than surprising.

2.2 The TCP/IP model: four layers, one journey

When your browser loads a page, the request is wrapped in headers by each layer on the way down and unwrapped on the way up at the other end. You mostly work at the top and the bottom; the middle layers matter when things break.

The single most useful diagnostic distinction Connection refused means your packet arrived and the machine actively said "nothing is listening here" — the network is fine, the service is not running or is bound to the wrong interface. Connection timed out means your packet vanished with no reply — almost always a firewall or security group silently dropping it. These two errors point at completely different teams.

2.3 IP addressing

An IP address identifies a network interface. IPv4 is four bytes, written as four decimal numbers 0–255: 192.168.1.34. That is about 4.3 billion addresses, which ran out — hence NAT (section 2.5) and IPv6.

IPv6 is eight groups of four hex digits, with :: collapsing one run of zeros:

2001:0db8:0000:0000:0000:ff00:0042:8329
2001:db8::ff00:42:8329        # same address, compressed
::1                           # IPv6 loopback (IPv4: 127.0.0.1)
# your addresses (modern command)
ip addr show
ip -4 addr show scope global    # just the routable IPv4 ones

# which interface and gateway will traffic to an address use?
ip route
ip route get 1.1.1.1
# 1.1.1.1 via 192.168.1.1 dev wlan0 src 192.168.1.34

Read that last line as the answer to three questions at once: the gateway (next hop), the interface traffic leaves by, and the source address it will appear to come from.

2.4 Subnets and CIDR

An address is split into a network part and a host part. CIDR notation says how many leading bits are the network part: 192.168.1.0/24 means the first 24 bits are the network, leaving 8 bits — 256 addresses — for hosts.

CIDRNetmaskTotal addressesUsable hostsTypical use
/32255.255.255.25511A single host, e.g. a firewall rule
/30255.255.255.25242Point-to-point link
/24255.255.255.0256254A small LAN, a cloud subnet
/16255.255.0.065,53665,534A VPC or a large private network
/8255.0.0.016,777,216—10.0.0.0/8, the big private block
/00.0.0.0everything—"Any address" — the default route

Two addresses in every subnet are reserved: the lowest is the network address and the highest is the broadcast address. That is why a /24 holds 256 addresses but only 254 hosts.

# 192.168.1.0/24
192.168.1.0     # network address — not assignable
192.168.1.1     # conventionally the router/gateway
192.168.1.2 ... 192.168.1.254   # usable hosts
192.168.1.255   # broadcast — not assignable
The two CIDR blocks you will type most 0.0.0.0/0 means "any IPv4 address anywhere". In a firewall rule it means the entire internet — correct for a public web port, alarming for a database port. Separately, binding a service to 0.0.0.0 means "listen on all interfaces", which is why every Dockerfile in this course runs uvicorn with --host 0.0.0.0: bound to 127.0.0.1 the service would be unreachable from outside its own container.

2.5 Private ranges, NAT and why your laptop is invisible

Three IPv4 ranges are reserved for private networks. They are not routable on the internet, so everyone reuses them:

RangeCIDRWhere you meet it
10.0.0.0 – 10.255.255.25510.0.0.0/8Cloud VPCs, Kubernetes pod networks
172.16.0.0 – 172.31.255.255172.16.0.0/12Docker's default bridge — usually 172.17.0.0/16
192.168.0.0 – 192.168.255.255192.168.0.0/16Home and office LANs
127.0.0.0 – 127.255.255.255127.0.0.0/8Loopback — never leaves the machine

NAT (Network Address Translation) is what lets many private addresses share one public one. Your router rewrites the source address and port of outbound packets, remembers the mapping, and reverses it on the way back.

Why NAT explains a whole class of problems NAT is directional. Outbound connections work because the router created a mapping when you initiated them. Inbound connections have no mapping, so they fail — which is why you can browse the web from your laptop but nobody can browse to your laptop without explicit port forwarding.

Docker's -p 8080:80 is exactly this: a port-forwarding rule from the host into the container's private network. Kubernetes NodePort is the same idea again. Once you see NAT, you see it everywhere in this course.

2.6 TCP vs UDP

TCPUDP
ConnectionYes — three-way handshake firstNo — just send
DeliveryGuaranteed, retransmits lossesBest effort, no retry
OrderingReassembled in orderMay arrive out of order
OverheadHigher (ACKs, state, congestion control)Minimal
Used byHTTP, HTTPS, SSH, Redis, Postgres, SMTPDNS (usually), NTP, VoIP, video, QUIC

TCP opens a connection with a three-way handshake — and knowing its shape makes tcpdump output readable:

client → server   SYN            # "can we talk?"
server → client   SYN, ACK       # "yes, can we?"
client → server   ACK            # "yes" — connection established

If you see SYN repeated with no reply, packets are being dropped — a firewall. If you see SYN answered with RST (reset), the host is reachable but refusing — nothing is listening on that port. Same two diagnoses as section 2.2, now visible on the wire.

2.7 Ports and sockets

An IP address gets you to a machine; a port gets you to a program on it. Ports are 16-bit, so 1–65535.

  • 0–1023 — well-known. Binding these requires root. This is why containers running as a non-root user (Module 3) listen on 8000 rather than 80.
  • 1024–49151 — registered. Where most application services live: 3000, 5432, 6379, 8000, 8080.
  • 49152–65535 — ephemeral. Your client gets a random one of these for each outbound connection.

A connection is uniquely identified by a four-tuple, which is why thousands of clients can all talk to port 443 on one server without ambiguity:

(source IP, source port, destination IP, destination port)
(192.168.1.34, 51234, 93.184.216.34, 443)
# what is listening on this machine?
ss -tulpn
#  t=tcp  u=udp  l=listening  p=process  n=numeric (don't resolve names)

# is anything on 8000?
ss -tulpn | grep :8000

# established connections
ss -tn state established
Read the bind address, not just the port 
127.0.0.1:8000   # loopback only — unreachable from anywhere else
0.0.0.0:8000     # all IPv4 interfaces — reachable from the network
[::]:8000        # all IPv6 interfaces
A service bound to 127.0.0.1 inside a container is unreachable even with -p published, because the port forward delivers to the container's external interface and nothing is listening there. This is one of the most common Docker bugs, and it looks identical to "the container is broken".

2.8 DNS: how a name becomes an address

DNS is a distributed lookup from names to records. The resolution order on Linux matters when debugging:

  1. /etc/hosts — a local static file, checked first. Overrides everything.
  2. The resolver configured in /etc/resolv.conf (or systemd-resolved).
  3. That resolver recurses: root servers → .com → example.com's authoritative nameserver.
  4. The answer is cached everywhere along the way, for its TTL in seconds.
RecordMapsExample
AName → IPv4example.com → 93.184.216.34
AAAAName → IPv6example.com → 2606:2800:220:1::
CNAMEName → another namewww → example.com
MXDomain → mail serverUsed for email routing
TXTArbitrary textDomain ownership proofs, SPF
NSDomain → its nameserversDelegation
dig example.com +short
dig example.com A
dig example.com +trace          # watch the full recursion from the root
dig @1.1.1.1 example.com        # ask a specific resolver, bypassing yours

# what is my machine using to resolve?
cat /etc/resolv.conf
resolvectl status               # on systemd-resolved systems
TTL is why DNS changes "don't work" If a record has a TTL of 3600, resolvers worldwide may serve the old value for up to an hour after you change it. Before a planned migration, lower the TTL to 60 a day in advance, migrate, then raise it again. Lowering it at the moment you migrate does not help — the old, long TTL is already cached.
Where this returns in the course Docker runs a DNS server on its user-defined networks so redis resolves to the Redis container's IP (Module 3). Kubernetes runs CoreDNS so urlshort-redis resolves to a Service IP (Module 6). Both are ordinary DNS — the reason names work there and not on the default bridge is simply which resolver the container was handed.

2.9 HTTP: the request you will read a thousand times

HTTP is text over TCP. A request is a method, a path, headers, a blank line, then an optional body:

POST /shorten HTTP/1.1
Host: localhost:8000
Content-Type: application/json
Content-Length: 30

{"url":"https://example.com"}

And the response is a status line, headers, blank line, body:

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 46

{"code":"a1b2c3d","short_url":"/r/a1b2c3d"}

Status codes by class

ClassMeaningWhose faultOnes that matter here
2xxSuccess—200 OK, 201 Created, 204 No Content
3xxRedirect—301 permanent, 302/307 temporary
4xxClient errorThe caller400, 401 unauthenticated, 403 forbidden, 404, 429 rate-limited
5xxServer errorYou500, 502 bad gateway, 503 unavailable, 504 gateway timeout
Why the 4xx/5xx split runs through the rest of the course In Module 7 you alert on the 5xx rate and not the 4xx rate. A flood of 404s usually means a broken link or a scanner — annoying, not an outage. A flood of 500s means your code is failing. Alerting on the wrong one either wakes you needlessly or misses real breakage.

The distinction also decodes the gateway codes: 502 means the proxy reached your app and got garbage or a closed connection; 503 means the proxy had no healthy backend to send to at all — exactly what a failing Kubernetes readiness probe produces; 504 means your app accepted the request and was too slow to answer.

Talking HTTP by hand

curl -s localhost:8000/health              # body only
curl -i localhost:8000/health              # headers + body
curl -I https://example.com                # headers only (HEAD)
curl -v https://example.com 2>&1 | head -20  # the whole conversation incl. TLS

# POST some JSON
curl -X POST localhost:8000/shorten \
  -H 'content-type: application/json' \
  -d '{"url":"https://example.com"}'

# just the status code — the form used in CI and healthchecks
curl -s -o /dev/null -w '%{http_code}\n' localhost:8000/health

# do NOT follow redirects (default), or DO follow them
curl -sI localhost:8000/r/abc123
curl -sL localhost:8000/r/abc123

2.10 HTTPS and TLS

HTTPS is HTTP inside a TLS tunnel. TLS gives you three distinct things, and conflating them causes confusion:

  • Encryption — nobody in between can read the traffic.
  • Integrity — nobody can modify it undetected.
  • Authentication — you are talking to the server the certificate names. This is the part a self-signed certificate does not give you.

The handshake, simplified: the client says hello, the server presents a certificate containing its public key and a signature from a Certificate Authority, the client verifies that signature against its trust store, and they derive a shared symmetric key for the actual data.

# inspect a live certificate: who issued it, and when does it expire?
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

# expiry only — the check worth putting on a schedule
echo | openssl s_client -connect example.com:443 2>/dev/null \
  | openssl x509 -noout -enddate
Three TLS failures and what they actually mean
  • certificate has expired — the single most common self-inflicted outage in this category. Automate renewal (cert-manager, certbot) and alert on days remaining, not on the failure.
  • self-signed certificate / unable to verify — the chain does not lead to a trusted CA. Fine inside a lab; never paper over it in production with curl -k, which disables the authentication guarantee entirely.
  • hostname mismatch — the certificate is valid but for a different name. Usually SNI: one IP serves many sites, and the server needs the -servername to pick the right cert.

Where TLS terminates matters architecturally. Usually a load balancer or ingress controller holds the certificate and speaks plain HTTP to your app behind it. That is why your container listens on port 8000 with no certificate at all — and why, in Module 6, the app is happily HTTP inside the cluster while users see HTTPS.

2.11 Firewalls and the ports that matter

A firewall filters traffic by address, port and direction. The rule that matters most is the default: deny everything inbound, then allow only what you deliberately need.

PortProtocolServiceExpose to the internet?
22TCPSSHRestrict to known IPs or a VPN
53UDP/TCPDNSOnly if you run a public resolver
80TCPHTTPYes — usually just to redirect to 443
443TCPHTTPSYes
3306TCPMySQLNever
5432TCPPostgreSQLNever
6379TCPRedisNever — no auth by default
8000 / 8080TCPApp serversNo — put a proxy in front
9090 / 3000TCPPrometheus / GrafanaNo — authenticate first
6443TCPKubernetes APIRestrict tightly
Redis on 6379 has no password by default An open Redis is not "a database someone might find" — it is remote code execution in many configurations, and internet-wide scanners find a new one within minutes. The same is true of exposed Docker daemons (2375) and unauthenticated Kubernetes API servers. Databases belong on a private network, reachable only from the app. 
# ufw (Ubuntu's friendly front end to iptables)
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp
sudo ufw allow 80,443/tcp
sudo ufw enable
sudo ufw status verbose

# restrict SSH to one source network
sudo ufw allow from 203.0.113.0/24 to any port 22 proto tcp
Docker publishes past your firewall docker run -p 8080:80 writes its own iptables rules, which are evaluated before ufw's. So a port you believed ufw was blocking can still be open to the world. Either bind the publish to loopback — -p 127.0.0.1:8080:80 — or filter at the cloud security-group level, which sits outside the host entirely. This surprises a lot of people in production.

2.12 The troubleshooting toolkit

QuestionCommand
What are my addresses and routes?ip addr, ip route get 1.1.1.1
Is the host reachable at all?ping -c3 <host> (ICMP is often blocked — a failure is not proof)
Does the name resolve?dig +short <host>, getent hosts <host>
Is the port open from here?nc -vz <host> <port>
What is listening locally?ss -tulpn
Where does traffic get lost?traceroute <host> / mtr <host>
What is actually on the wire?sudo tcpdump -i any -n port 6379
Does the whole HTTP request work?curl -v <url>
Work up the layers, not randomly Resolve the name (DNS) → reach the host (IP) → reach the port (TCP) → get a valid response (HTTP). Each step tells you whether to keep going or stop and fix. Jumping straight to reading application logs when the name does not even resolve is how an afternoon disappears.

Lab: trace a request end to end

Goal Follow one HTTP request through every layer, then deliberately create — and diagnose — the four classic failures: wrong bind address, closed port, DNS failure, and expired-style TLS error.

Step 1 — your own network position

cd ~/devops/urlshort

ip -4 addr show scope global
ip route get 1.1.1.1
# note your source IP, gateway and interface

# is your address private or public?
ip -4 addr show scope global | grep -o 'inet [0-9.]*'
curl -s https://api.ipify.org; echo
# If these two differ, you are behind NAT — which you almost certainly are.

Step 2 — resolve a name, by hand

dig +short example.com
dig example.com +noall +answer      # see the TTL in the third column
dig example.com +trace | tail -20   # root -> .com -> authoritative

# prove /etc/hosts wins over DNS
echo "127.0.0.1 not-a-real-domain.test" | sudo tee -a /etc/hosts
getent hosts not-a-real-domain.test
dig +short not-a-real-domain.test   # empty — DNS never knew about it
sudo sed -i '/not-a-real-domain.test/d' /etc/hosts

Step 3 — the four-tuple, live

python3 -m http.server 8000 &
sleep 1

ss -tulpn | grep :8000
# LISTEN 0.0.0.0:8000  ← all interfaces

curl -s -o /dev/null localhost:8000
ss -tn state established '( dport = :8000 or sport = :8000 )'
# note the ephemeral client port (49152-65535) against server port 8000

Step 4 — failure 1: bound to loopback only

kill %1 2>/dev/null
python3 -m http.server 8001 --bind 127.0.0.1 &
sleep 1

ss -tulpn | grep :8001
# LISTEN 127.0.0.1:8001  ← NOT 0.0.0.0

curl -s -o /dev/null -w '%{http_code}\n' 127.0.0.1:8001    # 200

MYIP=$(ip -4 -o addr show scope global | awk '{print $4}' | cut -d/ -f1 | head -1)
curl -s -m 3 "http://$MYIP:8001" ; echo "exit=$?"
# Connection refused — this is the #1 container networking bug,
# and it is why every Dockerfile here uses --host 0.0.0.0
kill %1 2>/dev/null

Step 5 — failure 2: refused vs timed out

# nothing listening -> immediate REFUSED
time curl -s -m 5 http://localhost:9999 ; echo "exit=$?"

# dropped by a firewall somewhere -> hangs until timeout
time curl -s -m 5 http://10.255.255.1 ; echo "exit=$?"

# the same distinction with netcat
nc -vz localhost 9999
nc -vz -w 3 10.255.255.1 80
Time the two commands The refused case returns in milliseconds; the dropped case burns the full timeout. That timing difference alone tells you whether to go looking at the service or at a firewall — before you read a single log line.
If you are behind an HTTP proxy, curl will lie to you here With http_proxy / https_proxy set (common on corporate networks), curl connects to the proxy — which succeeds — and you get a proxy error such as exit 56 instead of the timeout. Check with env | grep -i proxy. Use curl --noproxy '*', or trust the nc results above: netcat ignores those variables and shows you the real behaviour.

Step 6 — failure 3: DNS

curl -s -m 5 http://no-such-host.invalid ; echo "exit=$?"
# curl: (6) Could not resolve host  — exit 6 is specifically DNS

dig +short no-such-host.invalid          # empty

dig +short example.com                   # has an address...
curl -s -m 3 https://example.com:444 ; echo "exit=$?"   # ...wrong port, exit 28 timeout

Step 7 — inspect real HTTP and TLS

Step 10 — a reusable port checker

cat > portcheck.sh <<'EOF'
#!/usr/bin/env bash
# portcheck.sh <host> <port>... — classify each port as open, refused or filtered
set -uo pipefail

HOST="${1:?usage: portcheck.sh <host> <port>...}"
shift
rc=0

for port in "$@"; do
  # -v so netcat reports WHY it failed; -w 2 caps the wait on dropped packets
  out=$(nc -zv -w 2 "$HOST" "$port" 2>&1)
  if [[ $? -eq 0 ]]; then
    printf 'open      %s:%s\n' "$HOST" "$port"
  elif grep -qi 'refused' <<<"$out"; then
    printf 'refused   %s:%s  (reachable, nothing listening)\n' "$HOST" "$port"
    rc=1
  else
    printf 'filtered  %s:%s  (no reply - firewall?)\n' "$HOST" "$port"
    rc=1
  fi
done
exit $rc
EOF

chmod +x portcheck.sh
./portcheck.sh example.com 80 443 6379 ; echo "exit=$?"
Keep this script It encodes the open/refused/filtered distinction you just learned, and you will reach for it in Module 3 (is the container's port published?), Module 4 (can the runner reach the service container?) and Module 6 (is the NodePort actually forwarded?).

git commit -m "feat: add portcheck helper for open/refused/filtered diagnosis"

Exercises

Exercise 1 — subnet arithmetic

For 10.42.7.0/22: how many addresses, how many usable hosts, what is the first and last address of the range, and is 10.42.9.200 inside it?

Solution

A /22 leaves 32 − 22 = 10 host bits, so 210 = 1024 addresses, 1022 usable.

A /22 block aligns on multiples of 4 in the third octet (256 × 4 = 1024), so this block runs from 10.42.4.0 to 10.42.7.255 — note the network address is not 10.42.7.0, which is why you check rather than assume.

10.42.9.200 is therefore outside it. Verify:

python3 -c "
import ipaddress
n = ipaddress.ip_network('10.42.7.0/22', strict=False)
print(n, n.num_addresses, n[0], n[-1])
print(ipaddress.ip_address('10.42.9.200') in n)"
# 10.42.4.0/22 1024 10.42.4.0 10.42.7.255
# False

Exercise 3 — a certificate expiry monitor

Write certcheck.sh <host> [days] that exits non-zero if the certificate expires within days (default 30).

Solution 
#!/usr/bin/env bash
set -euo pipefail

HOST="${1:?usage: certcheck.sh <host> [days]}"
DAYS="${2:-30}"

end=$(echo | openssl s_client -connect "$HOST:443" -servername "$HOST" 2>/dev/null \
      | openssl x509 -noout -enddate | cut -d= -f2)

end_epoch=$(date -d "$end" +%s)
now_epoch=$(date +%s)
left=$(( (end_epoch - now_epoch) / 86400 ))

if (( left < DAYS )); then
  echo "WARN: $HOST cert expires in ${left}d (threshold ${DAYS}d)" >&2
  exit 1
fi
echo "OK: $HOST cert valid for ${left}d"
./certcheck.sh example.com 30

Alerting on days remaining rather than on the expiry itself is the point — by the time the certificate has expired you are already in an outage, and this is exactly the "alert on a leading indicator" idea that returns in Module 7's predict_linear exercise.

Exercise 4 — the firewall that isn't

You set ufw default deny incoming and only allowed 22, 80 and 443. Yet colleagues can reach your Redis on 6379. How, and what are two correct fixes?

Solution

Redis is running in a container published with -p 6379:6379. Docker inserts its rules into the DOCKER chain, which iptables evaluates before ufw's INPUT rules — so the publish bypasses ufw entirely.

Fix 1 — bind the publish to loopback so it is never exposed:

docker run -d -p 127.0.0.1:6379:6379 redis:7-alpine

Fix 2 — do not publish it at all. Put Redis on a user-defined Docker network and let only the app container reach it by name. This is exactly what the Compose file in Module 3 does: the redis service has no ports: key, so it is reachable from the API container and from nowhere else.

A third, complementary layer in cloud environments: enforce it in the security group, which sits outside the host and cannot be bypassed by anything running on it.

Checkpoint

Your app runs in a container and logs "listening on 127.0.0.1:8000". You published it with -p 8080:8000, but requests are refused. Why?
The forward delivers to the container's interface, but the process only accepts traffic arriving on its own loopback. Bind to 0.0.0.0 — which is why every Dockerfile in this course passes --host 0.0.0.0.
One connection attempt fails instantly with "refused"; another hangs for 30 seconds then times out. What does that tell you?
The timing itself is the diagnosis. An RST comes back immediately from a reachable host; a dropped packet produces silence until your client gives up. Different problem, different team.
You lower a DNS record's TTL from 3600 to 60 and immediately change the record. Users still hit the old server. Why?
The new short TTL only applies to lookups made after the change. Lower the TTL well in advance of a migration — a day ahead — so every cached copy has already expired by the time you cut over.
You should now be able to, without notes:
  • Name the four TCP/IP layers and which failure each one produces.
  • Read CIDR notation, compute usable hosts, and say what 0.0.0.0/0 means in a firewall rule.
  • Explain why a service bound to 127.0.0.1 is unreachable, and when to use 0.0.0.0.
  • Distinguish "connection refused" from "connection timed out" and act on each differently.
