3.1 The problem containers solve

You write an app on Ubuntu with Python 3.12 and Redis 7. Your colleague runs macOS with Python 3.10. The server runs Debian with Python 3.9 and a Redis someone upgraded last year. The app behaves differently in all three places, and every difference costs a day.

The instinct — "write better install docs" — does not work, because the documentation describes the environment while the environment drifts. Containers invert this: instead of documenting the environment, you ship it. The runtime, the libraries, the OS packages and your code travel together as one immutable artefact.

Why it exists A container turns "an environment you must reproduce" into "a file you can copy". That is the whole idea, and everything else — Kubernetes, CI image builds, registries — is infrastructure built on top of that one property.

3.2 What a container actually is

A container is not a small virtual machine. A VM boots a full guest kernel on virtualised hardware — gigabytes, tens of seconds. A container is just a normal Linux process on the host kernel, with two kernel features applied to it:

  • Namespaces — the process gets its own view of the filesystem, network interfaces, process tree and hostname. It cannot see the host's other processes.
  • cgroups — the kernel caps how much CPU and memory that process may consume.

Two consequences you must internalise: containers start in milliseconds (so restarting one is a normal operation, not an emergency), and containers cannot run a different kernel (Linux containers on Windows/macOS run inside a hidden Linux VM).

3.3 Images, layers and the cache

An image is a read-only template. A container is a running instance of it. The relationship is exactly class-to-object.

Images are built in layers — each instruction in a Dockerfile adds one read-only layer. Layers are content-addressed and shared: if ten images use the same python:3.12-slim base, that base is stored once. When you start a container, Docker adds a thin writable layer on top; when the container is deleted, only that layer is lost.

Why layer order dominates build speed Docker caches layers. If an instruction and everything before it is unchanged, the cached layer is reused. But once one layer is invalidated, every layer after it rebuilds. So put what changes rarely (dependency installs) before what changes constantly (your source code). Getting this backwards turns a 3-second rebuild into a 3-minute one, on every single commit.

3.4 The commands you will use daily

# run: -d detached, -p host:container port, --name for a stable handle
docker run -d --name web -p 8080:80 nginx:1.27-alpine

docker ps              # running containers
docker ps -a           # including stopped ones
docker logs -f web     # follow stdout/stderr
docker exec -it web sh # a shell INSIDE the running container
docker stop web        # SIGTERM, then SIGKILL after 10s
docker rm web
docker images
docker rmi nginx:1.27-alpine

# reclaim disk — this WILL delete unused images and build cache
docker system df
docker system prune -a
Read -p 8080:80 as HOST:CONTAINER Traffic arriving on your machine's port 8080 is forwarded to port 80 inside the container. Getting this the wrong way round is a rite of passage; docker ps shows the mapping. This is precisely the NAT port-forwarding from Module 2.5 — the container sits on a private network and the publish creates the inbound mapping.

3.5 The application

Create the project and write the app you will carry through the rest of the course.

cd ~/devops/urlshort
mkdir -p app tests

app/main.py:

import os, hashlib
from fastapi import FastAPI, HTTPException
from fastapi.responses import RedirectResponse
from pydantic import BaseModel
import redis

REDIS_URL = os.getenv("REDIS_URL", "redis://localhost:6379/0")
r = redis.from_url(REDIS_URL, decode_responses=True)
app = FastAPI(title="urlshort")

class Link(BaseModel):
    url: str

@app.get("/health")
def health():
    try:
        r.ping()
    except Exception:
        raise HTTPException(status_code=503, detail="redis unavailable")
    return {"status": "ok"}

@app.post("/shorten")
def shorten(link: Link):
    code = hashlib.sha256(link.url.encode()).hexdigest()[:7]
    r.set(f"url:{code}", link.url)
    return {"code": code, "short_url": f"/r/{code}"}

@app.get("/r/{code}")
def follow(code: str):
    url = r.get(f"url:{code}")
    if not url:
        raise HTTPException(status_code=404, detail="unknown code")
    r.incr(f"hits:{code}")
    return RedirectResponse(url, status_code=307)

@app.get("/stats/{code}")
def stats(code: str):
    return {"code": code, "hits": int(r.get(f"hits:{code}") or 0)}

requirements.txt:

fastapi==0.115.0
uvicorn[standard]==0.30.6
redis==5.0.8
pydantic==2.9.2

Two design choices that matter later Redis is reached via an environment variable, not a hardcoded host — that is what lets the same image run against localhost, a Compose service and a Kubernetes Service without rebuilding. And /health genuinely checks the dependency instead of returning 200 unconditionally, which is what makes it useful as a Kubernetes probe in Module 6.

tests/test_api.py:

import os
os.environ.setdefault("REDIS_URL", "redis://localhost:6379/0")
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def test_health():
    assert client.get("/health").status_code == 200

def test_shorten_and_follow():
    res = client.post("/shorten", json={"url": "https://example.com"})
    assert res.status_code == 200
    code = res.json()["code"]
    assert len(code) == 7

    follow = client.get(f"/r/{code}", follow_redirects=False)
    assert follow.status_code == 307
    assert follow.headers["location"] == "https://example.com"

def test_unknown_code_is_404():
    assert client.get("/r/zzzzzzz", follow_redirects=False).status_code == 404

3.6 Writing a Dockerfile — three revisions

The instructive way to learn Dockerfiles is to write a bad one and fix it.

Revision 1 — works, and is wrong in four ways

FROM python:3.12
COPY . /app
WORKDIR /app
RUN pip install -r requirements.txt
CMD uvicorn app.main:app --host 0.0.0.0
  1. python:3.12 is ~1 GB; the -slim variant is ~130 MB.
  2. COPY . before pip install means every source edit reinstalls every dependency.
  3. It runs as root. A container escape is then a root escape.
  4. CMD in shell form makes your app a child of /bin/sh, so it never receives SIGTERM — shutdowns become 10-second kills.

Revision 2 — fix the ordering, the base, and the user

FROM python:3.12-slim

ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1

WORKDIR /app

# dependencies first: this layer is cached until requirements.txt changes
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# source last: edits here invalidate only this layer
COPY app/ ./app/

RUN useradd -m -u 10001 appuser
USER appuser

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
PYTHONUNBUFFERED=1 is not cosmetic Without it Python buffers stdout, so docker logs shows nothing until the buffer fills — and if the container crashes, the buffered lines are lost. You lose exactly the logs explaining the crash.

Revision 3 — multi-stage, for a smaller final image

Multi-stage builds let you use a fat image to compile and a thin one to run, copying only the artefacts across:

# ---- stage 1: build wheels ----
FROM python:3.12-slim AS builder
WORKDIR /build
RUN apt-get update && apt-get install -y --no-install-recommends gcc \
 && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip wheel --no-cache-dir --wheel-dir /wheels -r requirements.txt

# ---- stage 2: runtime ----
FROM python:3.12-slim
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
WORKDIR /app

COPY --from=builder /wheels /wheels
RUN pip install --no-cache-dir --no-index --find-links=/wheels /wheels/* \
 && rm -rf /wheels

COPY app/ ./app/

RUN useradd -m -u 10001 appuser && chown -R appuser:appuser /app
USER appuser

EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD python -c "import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://localhost:8000/health').status==200 else 1)"
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

The gcc toolchain exists only in the builder stage and never reaches the final image — smaller and less to attack.

3.7 Data: volumes and why containers are ephemeral

The container's writable layer dies with the container. This is a feature: it forces you to be explicit about what is genuinely state. Anything that must survive goes in a volume.

# named volume — Docker manages the location; use this for databases
docker volume create redis-data
docker run -d --name redis -v redis-data:/data redis:7-alpine \
  redis-server --appendonly yes

# bind mount — a host path; use this for live-reloading source in dev
docker run -d -p 8000:8000 -v "$(pwd)/app:/app/app" urlshort:dev

docker volume ls
docker volume inspect redis-data
Bind mounts are a development tool They couple the container to a host path that will not exist on a server. Use them for hot-reload while coding; never in a production definition.

3.8 Networking between containers

Containers on the same user-defined network reach each other by container name, resolved by Docker's built-in DNS. This is why the app can connect to redis://redis:6379 without knowing any IP address.

docker network create appnet
docker run -d --name redis --network appnet redis:7-alpine
docker run -d --name api --network appnet -p 8000:8000 \
  -e REDIS_URL=redis://redis:6379/0 urlshort:dev

# prove the DNS works, from inside the api container
docker exec -it api sh -c "getent hosts redis"
localhost inside a container means the container If your app is configured with redis://localhost:6379 and Redis is a different container, you get "connection refused" — the app is looking at its own network namespace. Use the service name. This is the single most common beginner error in this module.

Note the error is refused and not timed out: the packet reached a real interface that replied "nothing here", exactly as in Module 2.2. And the reason redis resolves at all is that Docker runs a DNS server on user-defined networks — ordinary DNS (Module 2.8), just with a different resolver.

3.9 Docker Compose

Typing those docker run flags by hand is error-prone and unreviewable. Compose puts the whole system in one declarative file that you commit to Git.

compose.yaml:

services:
  api:
    build: .
    ports:
      - "8000:8000"
    environment:
      REDIS_URL: redis://redis:6379/0
    depends_on:
      redis:
        condition: service_healthy
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
    restart: unless-stopped

volumes:
  redis-data:
Why condition: service_healthy and not plain depends_on Plain depends_on waits for the container to start, not to be ready. Redis takes a moment to accept connections, so the API starts, fails to connect, and crashes. Gating on the healthcheck fixes a race you would otherwise spend an hour on. 
docker compose up -d --build
docker compose ps
docker compose logs -f api
docker compose exec api sh
docker compose down          # stop + remove containers, KEEP volumes
docker compose down -v       # ... and delete volumes too (destroys data)

A development override

Compose merges compose.override.yaml automatically, so dev-only settings stay out of the file you deploy. compose.override.yaml:

services:
  api:
    volumes:
      - ./app:/app/app
    command: ["uvicorn", "app.main:app", "--host", "0.0.0.0",
               "--port", "8000", "--reload"]

3.10 Debugging a container that won't start

Work down this list in order. It resolves nearly every case:

StepCommandWhat you learn
1. Did it exit?docker compose ps -aExit code. 137 = OOM-killed. 1 = your app crashed. 127 = command not found.
2. What did it say?docker compose logs apiThe stack trace. Usually the whole answer.
3. Is the image right?docker run --rm -it urlshort shPoke around the filesystem; is your code where you think?
4. Is the env right?docker compose exec api envMissing or misspelled variables.
5. Can it reach its dependency?docker compose exec api sh -c "getent hosts redis"DNS/network problem vs. app problem.
6. Is the port mapped?docker compose psHost:container mapping, and whether it bound at all.
When the container exits instantly and logs are empty Override the entrypoint to get a shell instead of your app: 
docker run --rm -it --entrypoint sh urlshort:dev
Then run your CMD by hand and read the error directly.

3.11 Registries and tagging

A registry is where images live so other machines can pull them. You will use GitHub Container Registry (GHCR) because it is free for public images and integrates with Actions in Module 4.

# create a Personal Access Token with write:packages scope, then:
echo "$GHCR_TOKEN" | docker login ghcr.io -u <your-username> --password-stdin

docker build -t ghcr.io/<you>/urlshort:0.1.0 .
docker tag ghcr.io/<you>/urlshort:0.1.0 ghcr.io/<you>/urlshort:latest
docker push ghcr.io/<you>/urlshort:0.1.0
docker push ghcr.io/<you>/urlshort:latest
Never deploy :latest latest is a mutable label, not a version. Two servers pulling "latest" a minute apart can run different code, and you cannot roll back to a tag that has been overwritten. Deploy immutable tags — a semantic version or the Git commit SHA. Module 4 tags images with the SHA automatically for exactly this reason.

CODE=$(curl -s -X POST localhost:8000/shorten -H 'content-type: application/json' \
  -d '{"url":"https://example.com"}' | grep -o '"code":"[^"]*"' | cut -d'"' -f4)
echo "code=$CODE"

Exercises

Exercise 1 — shrink the image

Get the final image under 150 MB without breaking it. Measure before and after.

Solution

Switch the runtime stage to python:3.12-alpine, and prune anything not needed at runtime. Verify:

docker images urlshort --format "{{.Tag}}\t{{.Size}}"

Caveat worth knowing: Alpine uses musl instead of glibc, so packages with C extensions may need compiling. For pure-Python dependencies Alpine is a clear win; when wheels stop resolving, slim is the pragmatic choice. Smaller is not automatically better.

Exercise 2 — resource limits

Constrain the API to 256 MB of memory and half a CPU in Compose, then confirm the limit is real.

Solution 
services:
  api:
    deploy:
      resources:
        limits:
          cpus: "0.5"
          memory: 256M
docker stats --no-stream
# MEM USAGE / LIMIT shows ... / 256MiB

Exceeding the memory limit gets the container OOM-killed with exit code 137 — worth recognising, since it looks like a mysterious crash if you do not know the number.

Exercise 3 — a second app instance

Run two API replicas behind Compose and confirm both share the same Redis.

Solution 
docker compose up -d --scale api=2
# fails: both want host port 8000

Remove the ports mapping from api and add an nginx service that proxies to api:8000 — Docker's DNS round-robins between the replicas. This is the moment you feel the limits of Compose, and precisely the problem Kubernetes exists to solve (Module 6).

Exercise 4 — read a Dockerfile critically

What are the three problems here?

FROM ubuntu:latest
RUN apt-get update
RUN apt-get install -y python3 python3-pip
COPY . .
RUN pip3 install -r requirements.txt
ENV DB_PASSWORD=supersecret
CMD python3 app.py
Solution
  1. update and install in separate layers: a cached update layer means install can pull stale or missing packages. Combine them with && and clean /var/lib/apt/lists in the same layer.
  2. ENV DB_PASSWORD bakes a secret into the image permanently — anyone who pulls it can read it with docker history. Secrets are injected at runtime, never built in.
  3. COPY . . before dependency install destroys the cache; also ubuntu:latest is unpinned, so the same Dockerfile builds differently next month.

Checkpoint

Your image rebuilds dependencies on every source change. What is wrong?
Invalidating a layer invalidates everything after it. Copy the dependency manifest, install, then copy the source — the install layer then stays cached until dependencies genuinely change.
Your API container logs Connection refused to localhost:6379, but the Redis container is healthy. Why?
Each container has its own network namespace. Use the Compose service name — redis://redis:6379/0 — which Docker's DNS resolves for you.
Why should you not deploy :latest?
Deployments must be reproducible. Immutable tags — a semver or the commit SHA — mean the running version is knowable and a rollback is a real option.
