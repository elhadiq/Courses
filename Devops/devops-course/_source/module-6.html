Module 06 · ~6 hours

Kubernetes: Orchestration

Compose runs containers on one machine and gives up when that machine dies. Kubernetes runs containers across many machines and keeps running when things fail — which is a different problem, and the reason it is more complicated.

6.1 What Kubernetes is for (and when not to)

Kubernetes solves a specific set of problems that appear once you run containers seriously:

  • Self-healing — a container crashes or a node dies; replacements start elsewhere automatically.
  • Scaling — go from 2 to 20 replicas with one field, manually or on a metric.
  • Zero-downtime releases — rolling updates with automatic rollback when the new version fails to become healthy.
  • Service discovery and load balancing — stable names in front of ephemeral pods.
  • Declarative configuration — the cluster continuously works to make reality match your YAML.
When not to use it Kubernetes has a real operational cost: control plane upgrades, networking, RBAC, storage classes, and a learning curve for everyone on the team. For a single app on a single server with modest traffic, Compose plus a good deployment script is often the better engineering decision. Choose Kubernetes when you have multiple services, need resilience across machines, or a platform team to own it — not because it is on job listings.

6.2 Architecture and the reconciliation loop

The single idea underneath all of Kubernetes is the reconciliation loop. You declare desired state. Controllers observe actual state. When they differ, controllers act. Forever, continuously.

Why this shape matters in practice You never tell Kubernetes to "start a container". You tell it "three replicas of this should exist", and something else works out how. Kill a pod and it comes back — not because a script noticed, but because the desired state never changed. This is the same observe/compare/act loop as terraform apply in Module 5, except it runs every few seconds instead of when you type it.

6.3 The objects you need

ObjectWhat it is
PodOne or more containers sharing a network namespace and storage. The smallest deployable unit. Ephemeral by design.
DeploymentManages a ReplicaSet, which manages Pods. Gives you replicas, rolling updates and rollback.
ServiceA stable virtual IP and DNS name in front of a changing set of Pods.
ConfigMapNon-secret configuration, injected as env vars or files.
SecretSame, for sensitive data. Base64-encoded, not encrypted by default.
NamespaceA logical partition of the cluster for isolation and quotas.
IngressHTTP routing from outside the cluster to Services, by host and path.
StatefulSetLike a Deployment but with stable identities and per-pod storage — for databases.
PersistentVolumeClaimA request for durable storage that outlives the Pod.

6.5 Pods and why you never create one directly

A bare Pod has no supervisor. If it dies, nothing brings it back; if its node dies, it is simply gone. Pods are the unit Kubernetes schedules, but a controller should always own them.

kubectl run tmp --image=busybox --restart=Never -- sleep 3600
kubectl get pods
kubectl delete pod tmp
kubectl get pods    # gone forever — nothing recreates it

Useful in practice for a one-off debugging shell inside the cluster network:

kubectl run debug --rm -it --image=nicolaka/netshoot --restart=Never -- sh
# inside: nslookup, curl, dig, tcpdump against cluster services

6.6 Deployments: replicas, rollouts, rollbacks

k8s/deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: urlshort-api
  labels: { app: urlshort, component: api }
spec:
  replicas: 3

  selector:
    matchLabels: { app: urlshort, component: api }

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # at most 1 extra pod above replicas during rollout
      maxUnavailable: 0    # never drop below 3 healthy — true zero downtime

  template:
    metadata:
      labels: { app: urlshort, component: api }
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
      containers:
        - name: api
          image: urlshort:0.1.0
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8000
          env:
            - name: REDIS_URL
              valueFrom:
                configMapKeyRef: { name: urlshort-config, key: REDIS_URL }
          resources:
            requests: { cpu: 50m, memory: 64Mi }
            limits:   { cpu: 500m, memory: 256Mi }
          livenessProbe:
            httpGet: { path: /health, port: 8000 }
            initialDelaySeconds: 10
            periodSeconds: 15
            failureThreshold: 3
          readinessProbe:
            httpGet: { path: /health, port: 8000 }
            initialDelaySeconds: 3
            periodSeconds: 5
            failureThreshold: 2
maxUnavailable: 0 is the setting people forget The default is 25%, meaning a quarter of your capacity can be down mid-rollout. With maxUnavailable: 0 and maxSurge: 1, Kubernetes starts a new pod, waits for it to be ready, then removes an old one. The rollout is slower and genuinely lossless.

Rollouts

kubectl apply -f k8s/deployment.yaml
kubectl rollout status deployment/urlshort-api

# trigger a rollout by changing the image
kubectl set image deployment/urlshort-api api=urlshort:0.2.0
kubectl rollout status deployment/urlshort-api

kubectl rollout history deployment/urlshort-api
kubectl rollout undo deployment/urlshort-api               # back one revision
kubectl rollout undo deployment/urlshort-api --to-revision=1
A failed rollout does not take you down If new pods never become ready, the rollout stalls with the old pods still serving. That is the readiness probe doing its job — which is why probes are not optional decoration.

6.7 Services and cluster DNS

Pods get new IPs on every restart, so you never address them directly. A Service provides a stable virtual IP and a DNS name, selecting pods by label.

apiVersion: v1
kind: Service
metadata:
  name: urlshort-api
spec:
  type: ClusterIP
  selector: { app: urlshort, component: api }
  ports:
    - port: 80          # the Service's port
      targetPort: 8000  # the container's port
TypeReachable fromUse for
ClusterIPInside the cluster only (default)Internal services — the common case
NodePortAny node's IP on a high port (30000–32767)Local development, kind clusters
LoadBalancerAn external IP from your cloud providerProduction entry points in cloud

DNS inside the cluster follows a fixed pattern:

urlshort-api                              # same namespace
urlshort-api.default                      # explicit namespace
urlshort-api.default.svc.cluster.local    # fully qualified
The most common Service bug The Service selector must match the pod template labels — not the Deployment's own labels. If they differ, the Service has zero endpoints and every request fails, while every pod looks perfectly healthy. Diagnose with: 
kubectl get endpoints urlshort-api
# ENDPOINTS <none>   ← selector matches nothing

6.8 ConfigMaps and Secrets

apiVersion: v1
kind: ConfigMap
metadata: { name: urlshort-config }
data:
  REDIS_URL: redis://urlshort-redis:6379/0
  LOG_LEVEL: info
---
apiVersion: v1
kind: Secret
metadata: { name: urlshort-secret }
type: Opaque
stringData:
  API_TOKEN: replace-me-in-a-real-secret-store
Kubernetes Secrets are encoded, not encrypted kubectl get secret x -o jsonpath='{.data.API_TOKEN}' | base64 -d prints the value, and by default they sit in etcd unencrypted. Treat them as "kept out of the manifest", not "protected". Real protection means enabling encryption at rest, restricting RBAC, and using an external store (External Secrets Operator, Vault, SOPS) — and never committing a Secret manifest with a live value.

Note that a pod does not automatically restart when a ConfigMap changes if you consume it as environment variables. You must trigger a rollout yourself:

kubectl rollout restart deployment/urlshort-api

6.9 Probes: the difference that causes outages

ProbeQuestionOn failure
startupHas it finished booting?Keeps the other probes from running yet. For slow starters.
readinessCan it serve traffic right now?Removed from the Service endpoints. Not restarted.
livenessIs it wedged beyond recovery?Container is killed and restarted.
The classic self-inflicted outage Your liveness probe checks /health, and /health checks the database. The database has a brief hiccup. Every pod fails liveness simultaneously and Kubernetes restarts your entire fleet — turning a 10-second database blip into a full outage, and hammering the recovering database with reconnects.

The rule: liveness checks only whether this process is stuck — usually a trivial endpoint returning 200. Readiness checks dependencies. That way a database blip removes pods from rotation temporarily and they return automatically, with no restarts.

6.10 Resources, requests and limits

  • requests — what the scheduler reserves. Determines which node a pod lands on.
  • limits — the hard ceiling. Exceed memory and the container is OOM-killed; exceed CPU and it is throttled, not killed.
resources:
  requests: { cpu: 50m, memory: 64Mi }   # 50m = 0.05 of a core
  limits:   { cpu: 500m, memory: 256Mi }
Pods with no requests are a scheduling hazard Without requests the scheduler assumes a pod needs nothing and packs nodes until they are exhausted, then evicts things unpredictably under pressure. Always set requests. Memory limits are important because memory is incompressible; CPU limits are more debatable, since throttling can hurt latency more than the noisy-neighbour problem they prevent.

6.11 Debugging a cluster methodically

kubectl get pods                          # status and restart count
kubectl describe pod <name>               # EVENTS at the bottom — read these first
kubectl logs <pod>
kubectl logs <pod> --previous             # logs from the container that just crashed
kubectl get events --sort-by=.lastTimestamp
kubectl exec -it <pod> -- sh
kubectl get endpoints <service>           # is the Service wired to anything?
kubectl port-forward svc/urlshort-api 8080:80
StatusMeansLook at
ImagePullBackOffCannot fetch the imageTag typo, private registry without imagePullSecrets, or image not loaded into kind
CrashLoopBackOffStarts, exits, repeatskubectl logs --previous — it is almost always your app
PendingNot scheduled onto any nodedescribe events: insufficient CPU/memory, or an unbound PVC
Running but not ReadyReadiness probe failingProbe path, port, and whether the dependency is up
OOMKilled / exit 137Exceeded the memory limitRaise the limit or fix the leak

Lab: deploy urlshort to Kubernetes

Goal Run the app on a real three-node cluster with Redis, config, probes, a rolling update, a rollback, and a self-healing demonstration.

Step 1 — cluster and image

cd ~/devops/urlshort
mkdir -p k8s
# create k8s/kind-config.yaml from section 5.4, then:
kind create cluster --name devops --config k8s/kind-config.yaml

# kind nodes cannot see your local Docker images — load it explicitly
docker build -t urlshort:0.1.0 .
kind load docker-image urlshort:0.1.0 --name devops
Forgetting kind load is the #1 error in this lab Symptom: ImagePullBackOff on an image that exists locally. The kind nodes are separate Docker containers with their own image store. Load it, or push to a registry the cluster can reach.

Step 2 — config and Redis

k8s/config.yaml:

apiVersion: v1
kind: ConfigMap
metadata: { name: urlshort-config }
data:
  REDIS_URL: redis://urlshort-redis:6379/0
  LOG_LEVEL: info

k8s/redis.yaml:

apiVersion: apps/v1
kind: Deployment
metadata: { name: urlshort-redis }
spec:
  replicas: 1
  selector: { matchLabels: { app: urlshort, component: redis } }
  template:
    metadata: { labels: { app: urlshort, component: redis } }
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          ports: [{ containerPort: 6379 }]
          resources:
            requests: { cpu: 25m, memory: 32Mi }
            limits:   { cpu: 200m, memory: 128Mi }
          readinessProbe:
            exec: { command: ["redis-cli", "ping"] }
            initialDelaySeconds: 2
            periodSeconds: 5
---
apiVersion: v1
kind: Service
metadata: { name: urlshort-redis }
spec:
  selector: { app: urlshort, component: redis }
  ports: [{ port: 6379, targetPort: 6379 }]

Step 3 — the API and its Service

Create k8s/deployment.yaml from section 5.6, plus k8s/service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: urlshort-api
  labels: { app: urlshort, component: api }   # Module 7's ServiceMonitor selects on these
spec:
  type: NodePort
  selector: { app: urlshort, component: api }
  ports:
    - name: http          # named port — Module 7 scrapes by name
      port: 80
      targetPort: 8000
      nodePort: 30080

Step 4 — apply and watch

kubectl apply -f k8s/config.yaml
kubectl apply -f k8s/redis.yaml
kubectl apply -f k8s/deployment.yaml
kubectl apply -f k8s/service.yaml

kubectl get pods -w
# Ctrl-C once all show Running and READY 1/1

kubectl get svc,endpoints
curl -s localhost:30080/health
# {"status":"ok"}

Step 5 — see the load balancing

kubectl get pods -l component=api -o name
# three pods

for i in $(seq 1 10); do
  curl -s -X POST localhost:30080/shorten \
    -H 'content-type: application/json' \
    -d '{"url":"https://example.com"}' > /dev/null
done

kubectl logs -l component=api --tail=5 --prefix
# requests spread across all three pods

Step 6 — self-healing

POD=$(kubectl get pods -l component=api -o jsonpath='{.items[0].metadata.name}')
kubectl delete pod "$POD"
kubectl get pods -l component=api
# a replacement is already ContainerCreating — you never asked for it

Step 7 — a rolling update with no dropped requests

# build a "v2"
docker build -t urlshort:0.2.0 .
kind load docker-image urlshort:0.2.0 --name devops

# in one terminal, hammer the endpoint:
while true; do curl -s -o /dev/null -w '%{http_code} ' localhost:30080/health; sleep 0.3; done

# in another, roll:
kubectl set image deployment/urlshort-api api=urlshort:0.2.0
kubectl rollout status deployment/urlshort-api

The first terminal should print an unbroken run of 200. That is maxUnavailable: 0 plus a readiness probe working together.

Step 8 — a failed rollout, and the rollback

kubectl set image deployment/urlshort-api api=urlshort:does-not-exist
kubectl rollout status deployment/urlshort-api --timeout=60s
# error: deployment exceeded its progress deadline

kubectl get pods -l component=api
# 3 old pods Running, 1 new pod ImagePullBackOff — traffic is UNAFFECTED

kubectl rollout undo deployment/urlshort-api
kubectl rollout status deployment/urlshort-api
Read that again You deployed a completely broken image to production and no user noticed. The bad pod never became ready, so it never entered the Service, so it never received traffic. That is what the whole probe/rollout machinery buys you.

Step 9 — break the Service selector on purpose

kubectl patch svc urlshort-api -p '{"spec":{"selector":{"app":"wrong"}}}'
kubectl get endpoints urlshort-api
# ENDPOINTS <none>
curl -s -m 3 localhost:30080/health || echo "no route to any pod"

kubectl patch svc urlshort-api -p '{"spec":{"selector":{"app":"urlshort","component":"api"}}}'
kubectl get endpoints urlshort-api    # three IPs again

Step 10 — commit, and clean up when done

cd ~/devops/urlshort
git add k8s
git commit -m "feat: kubernetes manifests with probes and rolling updates"
git push

# when you are finished for the day:
kind delete cluster --name devops

Exercises

Exercise 1 — persistent Redis

Give Redis a PersistentVolumeClaim so data survives pod deletion.

Solution 
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: redis-data }
spec:
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 1Gi } }
# in the redis pod spec:
      volumes:
        - name: data
          persistentVolumeClaim: { claimName: redis-data }
      containers:
        - name: redis
          command: ["redis-server", "--appendonly", "yes"]
          volumeMounts:
            - { name: data, mountPath: /data }

For real databases prefer a StatefulSet: it gives stable network identity and a volumeClaimTemplate per replica, which a Deployment cannot.

Exercise 2 — autoscaling

Scale the API between 2 and 10 replicas based on CPU.

Solution 
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
# on kind, patch for self-signed kubelet certs:
kubectl patch deployment metrics-server -n kube-system --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'

kubectl autoscale deployment urlshort-api --cpu-percent=70 --min=2 --max=10
kubectl get hpa -w

HPA requires resource requests to be set — the target percentage is measured against the request, so without one it has no denominator and does nothing.

Exercise 3 — namespaces and quotas

Move everything into a urlshort namespace and cap its total resource usage.

Solution 
kubectl create namespace urlshort
kubectl apply -f k8s/ -n urlshort

cat <<'EOF' | kubectl apply -n urlshort -f -
apiVersion: v1
kind: ResourceQuota
metadata:
  name: urlshort-quota
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 2Gi
    limits.cpu: "4"
    limits.memory: 4Gi
    pods: "20"
EOF

kubectl describe quota -n urlshort

Once a quota exists, any pod without requests and limits is rejected — which is a useful way to enforce the habit across a team.

Exercise 4 — diagnose from symptoms

Pods are Running and 1/1 Ready, but curl to the Service times out. Give the diagnostic sequence.

Solution 
kubectl get endpoints urlshort-api      # 1. <none> ⇒ selector mismatch
kubectl get svc urlshort-api -o yaml    # 2. targetPort vs containerPort
kubectl port-forward pod/<pod> 8000:8000 && curl localhost:8000/health
                                        # 3. bypass the Service: is the pod itself fine?
kubectl get pod <pod> -o jsonpath='{.spec.containers[0].ports}'

Work outward from the pod. If port-forward to the pod succeeds but the Service fails, the fault is in the Service definition — selector or targetPort, in that order of likelihood.

Checkpoint

Your liveness probe hits /health, which checks Redis. Redis restarts for 20 seconds. What happens?
Liveness failure means restart. Dependency checks belong in readiness, which only removes pods from rotation. Liveness should ask "is this process wedged", nothing more.
All pods are Running and Ready, but the Service returns nothing. First command?
Empty endpoints instantly tells you the Service selector does not match the pod template labels — a class of bug where everything looks healthy and nothing works.
Why did deploying a nonexistent image tag cause zero user impact?
Note it did not auto-roll-back — the rollout simply stalled safely, and you undid it deliberately. Readiness gating is what made a broken deploy a non-event.
You should now be able to, without notes:
  • Describe the reconciliation loop and say why you declare state rather than issue commands.
  • Explain Pod vs Deployment vs Service and why you never create a bare Pod.
  • Write a Deployment with probes, resources, a non-root security context and a safe rollout strategy.
  • Explain the difference between liveness and readiness, and the outage that confusing them causes.
  • Wire a Service to pods by label and debug empty endpoints.
  • Inject configuration via ConfigMap and say why Kubernetes Secrets are not really secret.
  • Perform a rolling update, recognise a stalled rollout, and roll back.
  • Diagnose ImagePullBackOff, CrashLoopBackOff, Pending and OOMKilled.
