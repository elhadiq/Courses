Infrastructure as Code: Terraform & Ansible

Stop clicking consoles and SSH-ing into servers to "just fix one thing". Declare what should exist, commit it, review it, and let a tool make reality match the file.

5.1 The problem: snowflake servers and drift

A server is set up by hand in 2023. Someone patches a config in 2024 during an outage. Someone else installs a debugging tool and forgets to remove it. By 2026 nobody knows what is on that machine, and nobody dares rebuild it because it cannot be reproduced. That is a snowflake: unique, fragile, and impossible to replace.

Configuration drift is how you get there — the slow, invisible divergence between what you think is deployed and what is actually deployed. Every manual change is a small increment of drift.

Why it exists Infrastructure as Code makes infrastructure obey the same rules as application code: it lives in Git, it is reviewed in a PR, changes are diffable, and rebuilding from scratch is a routine operation rather than a disaster-recovery exercise. The real payoff is that rebuilding becomes boring.

5.2 Declarative vs imperative

ImperativeDeclarative
You writeThe steps to takeThe end state you want
Exampleapt install nginx && systemctl start nginxnginx is installed and running
Run twiceMay error or duplicate workSecond run does nothing — already true
ToolsShell scriptsTerraform, Ansible modules, Kubernetes manifests

The declarative model gives you idempotency: applying the same configuration any number of times converges on the same result. That property is what makes automation safe to re-run, which is what makes it usable at all — an automation you are afraid to run twice is not automation.

5.3 Terraform vs Ansible — the division of labour

Beginners often ask which one to learn. They solve adjacent problems and are commonly used together.

TerraformAnsible
JobProvisioning: create the things — networks, VMs, databases, DNS, load balancersConfiguration: make an existing machine correct — packages, files, services, users
ModelDeclarative, with persistent stateMostly declarative modules, executed in order, stateless
Knows aboutWhat it created (via state file)Nothing between runs — it inspects each time
TransportProvider APIsSSH (agentless)
Deletingterraform destroy removes what it madeNo concept of teardown

Typical flow: Terraform creates three VMs and outputs their IPs → Ansible connects to those IPs and installs Docker, deploys config, starts services.

5.4 Terraform: the core loop

terraform init      # download providers, set up the backend. Run once per project/change.
terraform fmt       # canonical formatting — put this in CI
terraform validate  # syntax and internal consistency
terraform plan      # show me what you WOULD change. Read this. Every time.
terraform apply     # make it so
terraform destroy   # tear it all down
plan is the safety mechanism, not a formality Read the plan symbols before typing yes: + create, ~ update in place, - destroy, -/+ destroy and recreate. That last one is where production databases die. When you see -/+ on something stateful, stop and find out which attribute forced it.

5.5 HCL: variables, outputs, resources, data

This course uses the Docker provider so everything runs locally with no cloud bill — the concepts are identical to AWS or Azure providers, only the resource names change.

terraform/main.tf:

terraform {
  required_version = ">= 1.6"
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0"
    }
  }
}

provider "docker" {}

# a network, so containers can find each other by name
resource "docker_network" "app" {
  name = "${var.project}-net"
}

# a named volume for redis persistence
resource "docker_volume" "redis_data" {
  name = "${var.project}-redis-data"
}

# pull the image (data-like resource: describes something external)
resource "docker_image" "redis" {
  name         = "redis:7-alpine"
  keep_locally = true
}

resource "docker_container" "redis" {
  name  = "${var.project}-redis"
  image = docker_image.redis.image_id

  command = ["redis-server", "--appendonly", "yes"]

  networks_advanced {
    name    = docker_network.app.name
    aliases = ["redis"]
  }

  volumes {
    volume_name    = docker_volume.redis_data.name
    container_path = "/data"
  }

  restart = "unless-stopped"
}

terraform/variables.tf:

variable "project" {
  description = "Name prefix for all resources"
  type        = string
  default     = "urlshort"
}

variable "api_port" {
  description = "Host port to expose the API on"
  type        = number
  default     = 8000

  validation {
    condition     = var.api_port > 1024 && var.api_port < 65536
    error_message = "api_port must be an unprivileged port."
  }
}

variable "api_image" {
  description = "Fully qualified image, ideally tagged with a commit SHA"
  type        = string
  default     = "urlshort:0.1.0"
}

terraform/outputs.tf — outputs are how Terraform hands facts to the next tool:

output "api_url" {
  description = "Where the API is reachable"
  value       = "http://localhost:${var.api_port}"
}

output "network_name" {
  value = docker_network.app.name
}

Dependencies are inferred, not declared

Because docker_container.redis references docker_network.app.name, Terraform knows the network must exist first. You almost never write explicit ordering — it builds a dependency graph from the references and parallelises everything unrelated. Use depends_on only for dependencies that exist in reality but not in the code.

5.6 State — the concept that trips everyone

Terraform records what it created in terraform.tfstate: a mapping from your resource addresses to real object IDs. Without it, Terraform cannot tell "this container does not exist yet" from "this container exists and I made it".

Three rules about state
  • Never commit it. It contains resource attributes including, frequently, secrets in plaintext. terraform.tfstate* and .terraform/ go in .gitignore.
  • Never hand-edit it. Use terraform state mv / rm / import.
  • For teams, use a remote backend with locking (S3 + DynamoDB, Terraform Cloud, GCS). Two concurrent applies against local state corrupt it and can duplicate or orphan real infrastructure.

The three commands that rescue you

# someone created a resource by hand; adopt it into state
terraform import docker_container.api <container-id>

# stop managing something without destroying it
terraform state rm docker_container.api

# see what Terraform thinks exists
terraform state list
terraform state show docker_container.redis

5.7 Modules and environments

A module is just a directory of .tf files you can call with different inputs. It is how you avoid copy-pasting staging into production and letting them drift apart.

terraform/
├── modules/
│   └── app/
│       ├── main.tf
│       ├── variables.tf
│       └── outputs.tf
└── envs/
    ├── dev/main.tf
    └── prod/main.tf
# envs/dev/main.tf
module "app" {
  source = "../../modules/app"

  project   = "urlshort-dev"
  api_port  = 8000
  api_image = "urlshort:0.1.0"
  replicas  = 1
}

Same code, different inputs — so staging is genuinely a smaller copy of production rather than a different system that resembles it.

5.8 Ansible: configuring what exists

Ansible connects over SSH and runs modules — small idempotent units like apt, copy, service. No agent to install on the target.

ansible/inventory.ini — the machines:

[web]
web1 ansible_host=203.0.113.10
web2 ansible_host=203.0.113.11

[web:vars]
ansible_user=ubuntu
ansible_ssh_private_key_file=~/.ssh/id_ed25519

[local]
localhost ansible_connection=local

ansible/playbook.yml:

- name: Configure application hosts
  hosts: web
  become: true

  vars:
    app_user: urlshort
    app_dir: /srv/urlshort

  tasks:
    - name: Install base packages
      ansible.builtin.apt:
        name: [ca-certificates, curl, gnupg]
        state: present
        update_cache: true
        cache_valid_time: 3600

    - name: Create the service account
      ansible.builtin.user:
        name: "{{ app_user }}"
        system: true
        create_home: false

    - name: Create the app directory
      ansible.builtin.file:
        path: "{{ app_dir }}"
        state: directory
        owner: "{{ app_user }}"
        mode: "0755"

    - name: Render the compose file
      ansible.builtin.template:
        src: compose.yaml.j2
        dest: "{{ app_dir }}/compose.yaml"
        owner: "{{ app_user }}"
        mode: "0644"
      notify: Restart the stack

    - name: Ensure Docker is enabled and running
      ansible.builtin.service:
        name: docker
        state: started
        enabled: true

  handlers:
    - name: Restart the stack
      ansible.builtin.command:
        cmd: docker compose up -d
        chdir: "{{ app_dir }}"
Why handlers exist A handler runs only if a task reported changed, and only once at the end of the play even if ten tasks notified it. So "restart the service" happens exactly when the config actually changed — not on every run, and not three times. That is the difference between a playbook you run daily and one you are scared to run. 
ansible -i inventory.ini web -m ping        # connectivity check
ansible-playbook -i inventory.ini playbook.yml --check --diff   # dry run
ansible-playbook -i inventory.ini playbook.yml
ansible-playbook -i inventory.ini playbook.yml --tags config    # subset

5.9 Idempotency, concretely

Run a playbook twice. The second run should report changed=0. If it does not, some task is doing work unconditionally, and you cannot trust the report to tell you what actually changed.

PLAY RECAP
web1 : ok=6  changed=4  unreachable=0  failed=0    # first run
web1 : ok=6  changed=0  unreachable=0  failed=0    # second run — correct
The command module is the usual culprit command and shell always report changed, because Ansible cannot know what your command did. Prefer a real module when one exists; when you must shell out, guard it: 
- name: Initialise the database once
  ansible.builtin.command: /srv/app/init-db.sh
  args:
    creates: /srv/app/.db-initialised   # skip if this file exists
creates/removes, or register + when, or changed_when — these turn an imperative escape hatch back into something idempotent.

5.10 Secrets in infrastructure code

IaC repositories are where secrets go to leak, because infrastructure genuinely needs credentials and the files are genuinely committed.

# Ansible Vault: encrypt a file in place
ansible-vault create group_vars/web/vault.yml
ansible-vault edit  group_vars/web/vault.yml
ansible-playbook playbook.yml --ask-vault-pass

For Terraform, mark sensitive values so they are not printed:

variable "db_password" {
  type      = string
  sensitive = true
}

output "connection_string" {
  value     = "postgres://app:${var.db_password}@db:5432/app"
  sensitive = true
}
sensitive = true hides it from output, not from state The value is still stored in plaintext in terraform.tfstate. Real protection means an encrypted remote backend plus a secrets manager (Vault, AWS Secrets Manager, SOPS) that Terraform reads from at apply time rather than storing.

Lab: provision and configure, locally

Goal Replace the hand-written Compose file with Terraform-managed infrastructure, prove drift detection works, then use Ansible to configure the host idempotently.

Step 1 — set up

cd ~/devops/urlshort
mkdir -p terraform ansible
cd terraform

# append to the repo .gitignore
cat >> ../.gitignore <<'EOF'
.terraform/
terraform.tfstate
terraform.tfstate.backup
*.tfvars
EOF

Step 2 — write the config

Create main.tf, variables.tf and outputs.tf from section 4.5, then add the API container to main.tf:

resource "docker_container" "api" {
  name  = "${var.project}-api"
  image = var.api_image

  env = [
    "REDIS_URL=redis://redis:6379/0",
  ]

  ports {
    internal = 8000
    external = var.api_port
  }

  networks_advanced {
    name = docker_network.app.name
  }

  restart = "unless-stopped"
  depends_on = [docker_container.redis]
}

Step 3 — the loop

docker compose down          # clear the Module 3 stack first

terraform init
terraform fmt
terraform validate
terraform plan
# Plan: 5 to add, 0 to change, 0 to destroy.

terraform apply
# type: yes

terraform output
# api_url = "http://localhost:8000"

curl -s localhost:8000/health

Step 4 — see idempotency

terraform apply
# No changes. Your infrastructure matches the configuration.

Step 5 — cause drift, then detect and correct it

# change reality behind Terraform's back
docker rm -f urlshort-api

terraform plan
# docker_container.api has been deleted
# Plan: 1 to add, 0 to change, 0 to destroy.

terraform apply -auto-approve
docker ps --filter name=urlshort
What just happened Terraform refreshed state against reality, noticed the container was gone, and reconciled. This is the core loop of every IaC tool and every Kubernetes controller: observe actual, compare to desired, act on the difference. You will see the identical pattern in Module 6.

Step 6 — a change that forces replacement

terraform plan -var 'api_port=8080'
# ~ update in-place? No:
# -/+ destroy and then create replacement
#     ports { external = 8000 -> 8080 } # forces replacement

terraform apply -var 'api_port=8080' -auto-approve
curl -s localhost:8080/health

Notice that Terraform told you it would destroy something before doing it. That preview is the reason you read plans.

Step 7 — Ansible against localhost

cd ../ansible

cat > inventory.ini <<'EOF'
[local]
localhost ansible_connection=local
EOF

cat > site.yml <<'EOF'
- name: Prepare the application host
  hosts: local
  gather_facts: true

  vars:
    app_dir: "{{ ansible_env.HOME }}/devops/deployed"

  tasks:
    - name: Create the deployment directory
      ansible.builtin.file:
        path: "{{ app_dir }}"
        state: directory
        mode: "0755"

    - name: Render the environment file
      ansible.builtin.copy:
        dest: "{{ app_dir }}/.env"
        mode: "0600"
        content: |
          REDIS_URL=redis://redis:6379/0
          LOG_LEVEL=info
      notify: Report change

    - name: Check docker is available
      ansible.builtin.command: docker --version
      register: docker_version
      changed_when: false

    - name: Show docker version
      ansible.builtin.debug:
        msg: "{{ docker_version.stdout }}"

  handlers:
    - name: Report change
      ansible.builtin.debug:
        msg: "environment file changed - would restart the service here"
EOF

ansible-playbook -i inventory.ini site.yml

Step 8 — prove idempotency

ansible-playbook -i inventory.ini site.yml
# PLAY RECAP: changed=0   ← the whole point

Note changed_when: false on the command task. Without it, a read-only version check would report a change on every run and the handler would fire pointlessly.

Step 9 — commit

cd ~/devops/urlshort
git status                   # confirm terraform.tfstate is NOT listed
git add terraform ansible .gitignore
git commit -m "feat: manage infrastructure with terraform and ansible"
git push

Exercises

Exercise 1 — parameterise the whole stack

Add a redis_version variable and a terraform.tfvars.example file so a new engineer can bring the stack up without reading the code.

Solution 
# variables.tf
variable "redis_version" {
  type    = string
  default = "7-alpine"
}

# main.tf
resource "docker_image" "redis" {
  name = "redis:${var.redis_version}"
}
# terraform.tfvars.example  (commit THIS, not terraform.tfvars)
project       = "urlshort"
api_port      = 8000
api_image     = "ghcr.io/you/urlshort:sha-abc123"
redis_version = "7-alpine"

Exercise 2 — terraform in CI

Add a workflow that runs fmt -check, validate and plan on pull requests, but never apply.

Solution 
jobs:
  terraform:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: terraform } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform fmt -check -recursive
      - run: terraform init -backend=false
      - run: terraform validate

-backend=false lets validation run without credentials or state access — safe on untrusted PRs. A real plan needs state and therefore credentials, which is precisely why it belongs behind an environment gate rather than on every fork's PR.

Exercise 3 — make a playbook idempotent

This task reports changed every run. Fix it two different ways.

- name: Install docker compose plugin
  ansible.builtin.shell: curl -fsSL https://example.com/install.sh | sh
Solution

Guard on an artefact:

- name: Install docker compose plugin
  ansible.builtin.shell: curl -fsSL https://example.com/install.sh | sh
  args:
    creates: /usr/local/lib/docker/cli-plugins/docker-compose

Or check first and act conditionally:

- name: Check for the plugin
  ansible.builtin.stat:
    path: /usr/local/lib/docker/cli-plugins/docker-compose
  register: compose_bin

- name: Install docker compose plugin
  ansible.builtin.shell: curl -fsSL https://example.com/install.sh | sh
  when: not compose_bin.stat.exists

Best of all: use the ansible.builtin.apt module with the official repository, so idempotency is the module's problem rather than yours.

Exercise 4 — adopt an unmanaged resource

Create a Docker volume by hand, then bring it under Terraform management without destroying it.

Solution 
docker volume create orphan-data

# add to main.tf:
# resource "docker_volume" "orphan" { name = "orphan-data" }

terraform import docker_volume.orphan orphan-data
terraform plan
# No changes — state now matches both the config and reality

This is the standard path for adopting infrastructure that predates your IaC adoption: write the resource block to match what exists, import, then confirm the plan is empty. A non-empty plan means your block does not yet describe reality accurately.

Checkpoint

A colleague commits terraform.tfstate to fix a "works on my machine" issue. What is the main risk?
Both halves matter. The fix is a remote backend with locking — that solves sharing properly, which is the real need behind the instinct to commit it.
terraform plan shows -/+ destroy and then create replacement on your database. What do you do?
Replacement destroys the resource. The plan output names the forcing attribute — sometimes it can be avoided, sometimes it needs a backup-and-migrate plan. Either way it is a decision, not an approval.
Your playbook reports changed=7 on every run even though nothing is different. Why does that matter?
The changed count is your signal. When it is always noisy, you stop reading it — and a genuine unexpected change slips past unnoticed, which is the failure mode idempotency exists to prevent.
You should now be able to, without notes:
  • Explain configuration drift and why snowflake servers are a liability.
  • State the difference between declarative and imperative, and why idempotency follows from it.
  • Say which of Terraform and Ansible you reach for, and why they are complementary.
  • Run the full Terraform loop and read a plan's + ~ - -/+ symbols correctly.
  • Explain what state is, why it is never committed, and what remote backends solve.
  • Import an existing resource into management.
  • Write an Ansible playbook with variables, handlers and genuine idempotency.
  • Handle secrets in IaC without committing them.
