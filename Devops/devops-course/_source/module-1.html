Module 01 · ~5 hours

The Ground Floor: Linux, Shell & Git

Every other tool in this course is a program you run from a shell, on a Linux machine, against a Git repository. Get fluent here and the rest is much easier than it looks.

In this module 1.1 Why the terminal, still 1.2 The filesystem and moving around it 1.3 Permissions, users and sudo 1.4 Pipes: the idea that makes the shell powerful 1.5 Processes, ports and logs 1.6 Writing a real shell script 1.7 SSH and keys 1.8 Git: the mental model 1.9 Branching, merging and the conflict you will hit 1.10 A workflow a team can actually live with Lab: bootstrap the course repository Exercises Checkpoint

1.1 Why the terminal, still

Servers do not have a desktop. A production machine typically runs no graphical layer at all — it would consume memory and add attack surface for no benefit. When you connect to one, you get a text prompt and nothing else.

But the deeper reason is reproducibility. A sequence of clicks cannot be committed to Git, reviewed by a colleague, or replayed on a hundred machines. A sequence of commands can. Everything in DevOps flows from that one property: if you can type it, you can automate it; if you can only click it, you will do it by hand forever.

Why it exists The shell is a programming language whose primitives are programs. That is unusual and it is the source of its power — you compose small tools you did not write into behaviour nobody anticipated.

1.2 The filesystem and moving around it

Linux has a single tree rooted at /. There are no drive letters. Directories you will meet constantly:

PathWhat lives there
/etcSystem-wide configuration files. Text, always. /etc/nginx/nginx.conf, /etc/hosts.
/var/logLogs. Your first stop when something is broken.
/home/<user>Your files. Abbreviated ~.
/usr/bin, /usr/local/binInstalled programs. /usr/local/bin is for things you installed manually.
/tmpScratch space, wiped on reboot.
/optSelf-contained third-party software.
# where am I
pwd

# what's here — long, all files incl. hidden, human-readable sizes
ls -lah

# move: absolute path, relative path, home, previous directory
cd /var/log
cd ../..
cd ~
cd -

# make a nested tree in one shot
mkdir -p ~/devops/labs/module1

# copy a directory recursively; move/rename; delete
cp -r src/ backup/
mv notes.txt docs/notes.txt
rm -r build/
rm has no undo There is no recycle bin. rm -rf / with root privileges destroys the machine. Get in the habit of running ls on a glob before you rm it: ls *.log then rm *.log.

Reading files without opening an editor

cat  app.conf          # dump the whole file
less app.log           # scrollable pager: /search, n next, q quit
head -n 20 app.log     # first 20 lines
tail -n 50 app.log     # last 50 lines
tail -f  app.log       # follow live — you will use this constantly

Finding things

# find files by name, under a directory
find /etc -name "*.conf"

# find text inside files: recursive, show line numbers, ignore case
grep -rni "database_url" ./src

# which binary will actually run when I type this?
which docker
# /usr/bin/docker

1.3 Permissions, users and sudo

Every file has an owner, a group, and three permission triplets: owner / group / everyone else. ls -l shows them:

-rwxr-xr--  1 zouhair devs  2048 Aug  8 10:22 deploy.sh
│└┬┘└┬┘└┬┘    └──┬──┘ └─┬┘
│ │  │  │        │     └── group
│ │  │  └─ others: read only        
│ │  └──── group:  read + execute   
│ └─────── owner:  read+write+exec  
└───────── type: - file, d directory, l symlink

Numerically, read=4, write=2, execute=1. So 755 = owner 7 (rwx), group 5 (r-x), others 5 (r-x). The two you will use in practice:

chmod +x deploy.sh        # make a script runnable
chmod 600 ~/.ssh/id_ed25519  # private key: owner only, or SSH refuses it
chown -R app:app /srv/app # give a service account ownership

sudo runs one command as root. Use it for system changes; never for your own project files — if you find yourself typing sudo to edit code you wrote, ownership is wrong somewhere.

1.4 Pipes: the idea that makes the shell powerful

Every program has three streams: stdin (input), stdout (normal output), stderr (errors). The pipe | connects one program's stdout to the next one's stdin. That single mechanism lets you build one-off analysis tools in seconds.

# Top 5 IPs hitting your server, from an nginx access log:
cat access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head -5

# read the chain right-to-left as a question:
#   head -5     ... show the top five
#   sort -rn    ... of the largest counts
#   uniq -c     ... counted per distinct value
#   sort        ... (uniq needs sorted input)
#   awk '{$1}'  ... of the first field (the IP)

Redirection sends streams to files instead:

./build.sh > build.log          # stdout to file (overwrite)
./build.sh >> build.log         # append
./build.sh > out.log 2> err.log # separate the streams
./build.sh > all.log 2>&1       # both into one file
./noisy.sh > /dev/null 2>&1     # discard everything
Why this matters later CI pipelines, Docker builds and Kubernetes containers all communicate by writing to stdout/stderr. A container that logs to a file instead of stdout is a container whose logs you cannot see. That is a rule you will meet again in Module 3.

1.5 Processes, ports and logs

Three questions you will ask on every broken machine: Is it running? Is it listening? What did it say before it died?

# Is it running?
ps aux | grep nginx
top            # live view; press q to quit

# Is it listening, and on what port?
ss -tulpn | grep 8080
# tcp LISTEN 0 128 0.0.0.0:8080 ... users:(("python3",pid=4711,fd=3))

# What did it say?
journalctl -u nginx --since "10 min ago"   # systemd services
tail -f /var/log/syslog

# Stop it: TERM asks politely, KILL does not ask
kill 4711
kill -9 4711
"Port already in use" The single most common local error in this course. Find the culprit and decide deliberately: 
ss -tulpn | grep :8080
kill <pid>   # or change your app's port

1.6 Writing a real shell script

A script is a file of commands. But a script anyone else will run needs four things most tutorials skip: a shebang, strict mode, arguments, and an exit code.

#!/usr/bin/env bash
# deploy.sh — build and ship one service

set -euo pipefail
#  -e  exit immediately if any command fails
#  -u  error on undefined variables (catches typos in $VAR)
#  -o pipefail  a pipeline fails if ANY stage fails, not just the last

SERVICE="${1:-}"
TAG="${2:-latest}"

if [[ -z "$SERVICE" ]]; then
  echo "usage: $0 <service> [tag]" >&2
  exit 1
fi

echo "==> building $SERVICE:$TAG"
docker build -t "$SERVICE:$TAG" .

if docker run --rm "$SERVICE:$TAG" pytest -q; then
  echo "==> tests passed"
else
  echo "==> tests FAILED, not shipping" >&2
  exit 1
fi
Always quote your variables "$SERVICE", not $SERVICE. Unquoted, a value containing a space becomes two arguments and your script does something you did not intend. This is the number-one source of shell bugs.

Exit codes matter more than they look: 0 means success, anything else means failure. CI systems decide whether your pipeline is green purely by reading that number. Check the last one with echo $?.

1.7 SSH and keys

SSH gives you an encrypted shell on a remote machine. Passwords are the weak way; key pairs are the standard. You generate two files: a private key (never leaves your machine) and a public key (copied to every server and to GitHub).

ssh-keygen -t ed25519 -C "zouhair@laptop"
# Enter file: press Enter for the default ~/.ssh/id_ed25519
# Passphrase: use one. It encrypts the key at rest.

# copy the PUBLIC key to a server
ssh-copy-id user@203.0.113.10

# connect
ssh user@203.0.113.10

# run one command remotely and come straight back
ssh user@203.0.113.10 'df -h /'

For GitHub, paste the contents of ~/.ssh/id_ed25519.pub into Settings → SSH and GPG keys, then verify:

cat ~/.ssh/id_ed25519.pub
ssh -T git@github.com
# Hi zouhair! You've successfully authenticated...
The private key is the secret id_ed25519 never leaves your machine, is never committed, never pasted into a chat. Only the .pub file is shared. If a private key leaks, revoke it everywhere and regenerate.

1.8 Git: the mental model

Most Git confusion comes from not knowing which of four places a change is in. Learn these and the commands become obvious:

git init                       # create a repo here
git status                     # READ THIS AFTER EVERY COMMAND
git add file.py                # working dir -> staging
git add -p                     # stage hunk by hunk; forces you to review
git commit -m "Add rate limit" # staging -> local repo
git push origin main           # local repo -> remote

git log --oneline --graph --all  # the history, visually
git diff                       # unstaged changes
git diff --staged              # what a commit would contain

Undoing things

SituationCommand
Discard edits to a file, not yet stagedgit restore file.py
Unstage a file, keep the editsgit restore --staged file.py
Fix the last commit's message or contentsgit commit --amend
Undo last commit, keep changes in working dirgit reset --soft HEAD~1
Undo a commit that is already pushedgit revert <sha>
reset vs revert on shared branches reset rewrites history. On a branch other people have pulled, that forces everyone into a painful recovery. revert creates a new commit that undoes the old one — history stays intact. On main, always revert.

Commit messages

A commit message is documentation your future self reads at 2 a.m. during an incident. The convention most teams use:

feat: add per-IP rate limiting to /shorten
fix: handle Redis timeout instead of returning 500
docs: document the DATABASE_URL variable
refactor: extract link validation into its own module
chore: bump python base image to 3.12

Imperative mood ("add", not "added"), under ~60 characters, explaining why in the body if the why is not obvious. This convention also lets tools generate changelogs automatically.

.gitignore

Commit source, never build output or secrets:

__pycache__/
*.pyc
.venv/
node_modules/
.env
*.log
.terraform/
terraform.tfstate*
Removing a secret from history is hard Adding .env to .gitignore after committing it does nothing — it is still in history. Assume any secret ever pushed is compromised: rotate the credential, then clean history with git filter-repo. Prevention is the only good option.

1.9 Branching, merging and the conflict you will hit

A branch is a movable pointer to a commit. Creating one is instant and costs nothing, which is why Git-based workflows lean on them so heavily.

git switch -c feat/rate-limit    # create and switch (modern form)
... edit, add, commit ...
git push -u origin feat/rate-limit

# bring main's newest work into your branch before opening a PR
git switch main && git pull
git switch feat/rate-limit
git merge main

When both branches changed the same lines, Git stops and marks the file:

<<<<<<< HEAD
limit = 100
=======
limit = 250
>>>>>>> main

Git cannot know which is correct. Edit the file so it contains the code you actually want, delete all three marker lines, then:

git add limits.py
git commit          # completes the merge

1.10 A workflow a team can actually live with

Trunk-based development with short-lived branches is what most high-performing teams use, and it is what the rest of this course assumes:

  1. main is always deployable. It is protected — nobody pushes to it directly.
  2. Work happens on a branch that lives hours to two days, not weeks. Long branches guarantee painful conflicts.
  3. Open a Pull Request. CI runs automatically (Module 4). A human reviews.
  4. Merge when both CI and the reviewer are green. Delete the branch.

The reason branches must be short-lived is mechanical, not cultural: merge pain grows with the square of divergence. Two branches that each moved a little are easy to reconcile; two that each moved a lot are not.

Lab: bootstrap the course repository

Goal Create the repo you will use for the rest of the course, with a working script, a sane .gitignore, a branch, a merge and a deliberate conflict you resolve.

Step 1 — create the repo

mkdir -p ~/devops/urlshort && cd ~/devops/urlshort
git init -b main
git config user.name  "Your Name"
git config user.email "you@example.com"

Step 2 — a script that does something

cat > healthcheck.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail

URL="${1:-http://localhost:8000/health}"
TRIES="${2:-5}"

for i in $(seq 1 "$TRIES"); do
  code=$(curl -s -o /dev/null -w '%{http_code}' "$URL") || code=000
  if [[ "$code" == "200" ]]; then
    echo "OK  $URL responded 200 on attempt $i"
    exit 0
  fi
  echo "... attempt $i/$TRIES got $code, retrying in 2s"
  sleep 2
done

echo "FAIL $URL never returned 200" >&2
exit 1
EOF

chmod +x healthcheck.sh
./healthcheck.sh https://example.com

That last line should print OK. Now watch it fail correctly — this is the important half:

./healthcheck.sh http://localhost:9999/nope 2
echo "exit code was: $?"
# exit code was: 1
Why this script is shaped this way It retries (services take time to start), it takes arguments instead of hardcoding, it writes failures to stderr, and it exits non-zero on failure. Those four properties are exactly what a CI system and a Kubernetes probe need. You will reuse this file in Modules 4 and 6.

Step 3 — ignore, commit

printf '%s\n' '__pycache__/' '.venv/' '.env' '*.log' > .gitignore

echo "SECRET_KEY=hunter2" > .env          # deliberately untracked
git status                                # .env must NOT appear

git add .
git commit -m "chore: add healthcheck script and gitignore"
git log --oneline

Step 4 — branch, change, merge

git switch -c feat/configurable-timeout
sed -i 's/sleep 2/sleep "${DELAY:-2}"/' healthcheck.sh
git commit -am "feat: make retry delay configurable via DELAY"

git switch main
git merge feat/configurable-timeout
git branch -d feat/configurable-timeout

Step 5 — create a conflict on purpose, then resolve it

git switch -c fix/tries-10
sed -i 's/TRIES="${2:-5}"/TRIES="${2:-10}"/' healthcheck.sh
git commit -am "fix: default to 10 retries"

git switch main
sed -i 's/TRIES="${2:-5}"/TRIES="${2:-3}"/' healthcheck.sh
git commit -am "fix: default to 3 retries"

git merge fix/tries-10
# CONFLICT (content): Merge conflict in healthcheck.sh

Open healthcheck.sh, choose the value you want, delete the <<<<<<< / ======= / >>>>>>> lines, then:

git add healthcheck.sh
git commit -m "merge: resolve retry-count conflict, settle on 5"
git log --oneline --graph --all

Step 6 — push to GitHub

Create an empty repo named urlshort on GitHub (no README, no .gitignore), then:

git remote add origin git@github.com:<you>/urlshort.git
git push -u origin main

Step 7 — protect main

On GitHub: Settings → Branches → Add branch protection rule for main. Enable Require a pull request before merging. In Module 4 you will add Require status checks to pass once your CI exists.

Exercises

Exercise 1 — log analysis with pipes

Given an nginx-style access log, produce a count of requests per HTTP status code, sorted by frequency. Generate test data first:

printf '%s\n' \
 '10.0.0.1 - - "GET /a" 200' '10.0.0.2 - - "GET /b" 404' \
 '10.0.0.1 - - "GET /c" 200' '10.0.0.3 - - "GET /d" 500' \
 '10.0.0.2 - - "GET /e" 404' '10.0.0.1 - - "GET /f" 200' > access.log
Solution 
awk '{print $NF}' access.log | sort | uniq -c | sort -rn
#  3 200
#  2 404
#  1 500

$NF is awk's "last field", which is more robust than counting columns when the request path contains spaces.

Exercise 2 — a disk-space guard

Write diskguard.sh that takes a threshold percentage (default 80), checks usage of /, prints a warning and exits 1 if usage exceeds it, exits 0 otherwise.

Solution 
#!/usr/bin/env bash
set -euo pipefail
THRESHOLD="${1:-80}"
USED=$(df --output=pcent / | tail -1 | tr -dc '0-9')

if (( USED > THRESHOLD )); then
  echo "WARN: / is ${USED}% full (threshold ${THRESHOLD}%)" >&2
  exit 1
fi
echo "OK: / is ${USED}% full"

tr -dc '0-9' strips everything that is not a digit — simpler and safer than parsing the % sign out by hand.

Exercise 3 — recover a lost commit

Commit something, then run git reset --hard HEAD~1 to "lose" it. Recover it without having written down the SHA.

Solution 
git reflog
# a1b2c3d HEAD@{1}: commit: the one you thought you lost
git reset --hard a1b2c3d

reflog records every position HEAD has occupied for ~90 days. Almost nothing committed in Git is truly unrecoverable, which is worth knowing before you panic.

Exercise 4 — clean history

Make three commits: wip, wip2, fix typo. Squash them into one well-named commit before "opening a PR".

Solution 
git rebase -i HEAD~3
# keep the first as "pick", change the other two to "squash" (or "s")
# save; then write one good message in the editor that appears

Only rebase branches nobody else has pulled. Rewriting shared history is the one Git operation that genuinely ruins other people's afternoons.

Checkpoint

Your script runs curl … | grep 200 and the curl fails, but the script keeps going. Why?
Without pipefail, bash reports only the final stage's status. set -euo pipefail at the top of every script prevents this whole class of silent failure.
You accidentally pushed a commit to main containing an API key. What is the correct first action?
The key is already public the moment it is pushed — cleaning history does not un-leak it, and bots scrape public repos within minutes. Revocation first, cleanup second.
Why does the course insist branches live hours, not weeks?
It is a mechanical property, not a preference. Small, frequent integrations mean small, tractable conflicts — which is why continuous integration is called that.
You should now be able to, without notes:
  • Navigate a server, find a config file in /etc and follow a log with tail -f.
  • Chain grep/awk/sort/uniq to answer a question about a log file.
  • Find which process holds a port and stop it.
  • Write a script with strict mode, arguments, stderr output and correct exit codes.
  • Generate an SSH key pair and authenticate to GitHub with it.
  • Explain the four states of a change and pick the right undo command for each.
  • Create a branch, merge it, and resolve a conflict without panic.
