Module 04 · ~5 hours

CI/CD with GitHub Actions

Every push runs your tests. Every merge to main builds and publishes an image tagged with the commit that produced it. You stop being the build server.

4.1 What CI and CD actually mean

The terms are used loosely; the distinctions matter because they imply different amounts of risk.

TermMeansThe hard part
Continuous IntegrationEveryone merges into main at least daily, and every merge is automatically built and tested.Not the tooling — the discipline of small, frequent merges and a test suite you actually trust.
Continuous DeliveryEvery commit on main produces a deployable artefact. Deploying is a button someone presses.Making the artefact genuinely deployable, every time, with no manual steps.
Continuous DeploymentEvery green commit on main goes to production automatically.Test coverage and observability good enough that nobody needs to look first.
Why it exists Manual builds are unrepeatable and manual test runs get skipped under pressure — exactly when they matter most. A pipeline makes the safe path the only path: you cannot merge without the tests passing, so nobody has to remember to run them.

The most important property of a pipeline is not speed but trust. A suite that fails randomly teaches the team to re-run it and ignore it, which is worse than having no suite at all, because it costs time and provides false assurance.

4.2 Anatomy of a workflow

GitHub Actions files live in .github/workflows/*.yml. The hierarchy:

  • Event — what starts it: push, pull_request, schedule, workflow_dispatch (a manual button).
  • Job — runs on a fresh virtual machine. Jobs are parallel unless you declare needs.
  • Step — either run: (a shell command) or uses: (a reusable action).
  • Runner — the VM. GitHub's hosted ubuntu-latest is free for public repos.
Every job starts on a clean machine Nothing carries over between jobs — not installed packages, not the working directory, not built files. If job B needs something job A produced, either put them in the same job or pass it through an artifact or a registry. This surprises everyone once.

4.3 Your first pipeline: test on every push

.github/workflows/ci.yml:

name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run tests
        run: python -m pytest -q

Commit and push. Open the Actions tab on GitHub and watch it run. It will fail — there is no Redis on the runner, so /health returns 503. That failure is the next section.

4.4 Services: a real Redis for your tests

You have two options, and the choice is a genuine engineering decision rather than a detail.

Option A — mock Redis

Fast, no infrastructure, but you are testing against a fake. Bugs in how you actually use Redis (expiry semantics, connection loss, pipelining) go undetected.

Option B — a service container

Actions can start real containers alongside the job. Slower by seconds, but you test the real thing. For an app whose entire behaviour depends on Redis, this is the right call:

jobs:
  test:
    runs-on: ubuntu-latest

    services:
      redis:
        image: redis:7-alpine
        ports: ["6379:6379"]
        options: >-
          --health-cmd "redis-cli ping"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 5

    env:
      REDIS_URL: redis://localhost:6379/0

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12", cache: pip }
      - run: pip install -r requirements.txt
      - run: python -m pytest -q
Here localhost is correct Opposite of Module 3. Service containers have their ports published onto the runner's network, and your test process runs directly on the runner — not in a container. So localhost:6379 reaches Redis. If you instead run your tests inside a container, you would use the service name. The rule underneath both cases is the same: address things by where the client is running — which network namespace the process making the call sits in (Module 2.7).

4.5 Caching, and why pipelines get slow

A pipeline nobody waits for is a pipeline people bypass. Two caches carry most of the win.

Dependency cache — cache: pip in setup-python keys on your requirements.txt hash and restores the wheel cache. Free, one line.

Docker layer cache — by default each run builds from scratch. Buildx can push the cache into the registry:

- uses: docker/setup-buildx-action@v3

- uses: docker/build-push-action@v6
  with:
    context: .
    push: true
    tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
    cache-from: type=gha
    cache-to: type=gha,mode=max
Cache correctness beats cache speed A cache keyed too loosely serves stale artefacts and produces a green build of code that does not work. Always key on the hash of the file that defines the dependencies. If you ever suspect the cache, bump a version prefix in the key rather than debugging it for an hour.

4.6 Quality gates: lint, format, type, scan

Tests catch broken behaviour. These catch the rest, and — more usefully — they end style arguments in code review by making them a machine's decision.

  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }

      - run: pip install ruff
      - name: Lint
        run: ruff check .
      - name: Format check
        run: ruff format --check .

      - name: Scan filesystem for vulnerabilities
        uses: aquasecurity/trivy-action@0.24.0
        with:
          scan-type: fs
          severity: "HIGH,CRITICAL"
          exit-code: "1"

quality and test declare no needs, so they run in parallel — you get both sets of failures in one run instead of discovering the lint error after waiting for tests.

Shift left The cost of a defect grows by roughly an order of magnitude at each stage it survives: caught by a linter in your editor (seconds), by CI (minutes), by a reviewer (hours), in production (days, plus users). Every gate you add early is buying down that multiplier.

4.7 Build and publish the image

This job only runs after tests pass, and only on main — pull requests should not publish images.

  build:
    needs: [test, quality]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Derive tags
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,format=long
            type=raw,value=latest

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
Why tag with the commit SHA It makes the running system traceable in both directions: from a container you can find the exact commit, and from a commit you can find the exact image. During an incident, "which code is actually running right now" becomes a lookup instead of an investigation. latest is published as a convenience for humans, never used for deployment.

secrets.GITHUB_TOKEN is minted automatically per run and expires when the run ends — no PAT to create, store or rotate. Note it needs permissions: packages: write declared explicitly; the default is read-only, which is the correct default.

4.8 Secrets, and how pipelines leak them

Store secrets in Settings → Secrets and variables → Actions. Reference them as ${{ secrets.NAME }}. GitHub masks their values in logs.

- name: Deploy
  env:
    DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}
  run: ./scripts/deploy.sh
Four real leak paths
  • Echoing them. Masking is string matching. Base64-encode or split a secret and the mask misses it. Never print one, even "temporarily to debug".
  • pull_request_target on untrusted forks. That trigger runs with your secrets against a fork's code. A malicious PR can exfiltrate everything. Use plain pull_request unless you fully understand the difference.
  • Unpinned third-party actions. uses: some/action@v1 follows a mutable tag; if that repo is compromised, your next run executes attacker code with your token. For anything outside actions/ and vendors you trust, pin to a commit SHA.
  • Over-broad token permissions. Set permissions: per job at the minimum needed.

4.9 Deployment, environments and approvals

GitHub Environments (Settings → Environments) add protection rules to a job: required reviewers, wait timers, and branch restrictions. This is what turns continuous delivery into something an organisation will actually sign off on.

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: staging
      url: https://staging.example.com
    steps:
      - run: echo "deploying ${{ github.sha }} to staging"

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production      # configure "required reviewers" on this env
      url: https://example.com
    steps:
      - run: echo "deploying ${{ github.sha }} to production"

Deployment strategies, briefly

StrategyHowCost / benefit
RecreateStop old, start newSimple; has downtime. Fine for internal tools.
RollingReplace instances a few at a timeNo downtime, but two versions run simultaneously — your API must tolerate that. Kubernetes default (Module 6).
Blue/greenTwo full environments, flip the routerInstant rollback; costs double infrastructure during the switch.
CanarySend 5% of traffic to the new version, watch metrics, ramp upSafest; requires the observability you build in Module 7.

4.10 Designing a pipeline people trust

  • Fast feedback first. Lint before tests, unit before integration. Fail in 30 seconds, not 12 minutes.
  • Deterministic. No test that depends on wall-clock time, network flakiness or execution order. One flaky test poisons the credibility of the whole suite.
  • Build once, promote the artefact. Never rebuild between staging and production — you would be deploying a different artefact than the one you tested.
  • Every merge to main is releasable. If it is not, the pipeline is decoration.
  • Under 10 minutes. Beyond that, people context-switch away and stop watching.

Lab: the full pipeline

Goal A single workflow that lints, tests against real Redis, builds a SHA-tagged image, pushes it to GHCR, and blocks merges when anything fails.

Step 1 — the complete workflow

Create .github/workflows/ci.yml:

name: CI

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

env:
  IMAGE: ghcr.io/${{ github.repository }}

jobs:

  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12", cache: pip }
      - run: pip install ruff
      - run: ruff check .
      - run: ruff format --check .

  test:
    runs-on: ubuntu-latest
    services:
      redis:
        image: redis:7-alpine
        ports: ["6379:6379"]
        options: >-
          --health-cmd "redis-cli ping"
          --health-interval 5s --health-timeout 3s --health-retries 5
    env:
      REDIS_URL: redis://localhost:6379/0
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12", cache: pip }
      - run: pip install -r requirements.txt
      - run: python -m pytest -q --junitxml=report.xml
      - if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-report
          path: report.xml

  build:
    needs: [quality, test]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=sha,format=long
            type=raw,value=latest
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  smoke:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run the published image and probe it
        run: |
          docker network create smokenet
          docker run -d --name redis --network smokenet redis:7-alpine
          docker run -d --name api --network smokenet -p 8000:8000 \
            -e REDIS_URL=redis://redis:6379/0 \
            ghcr.io/${{ github.repository }}:sha-${{ github.sha }}
          chmod +x healthcheck.sh
          ./healthcheck.sh http://localhost:8000/health 15
      - if: failure()
        run: docker logs api
What the smoke job is really testing Unit tests prove your code is correct. The smoke job proves the artefact is correct — that the image you are about to deploy actually boots, finds its dependency and serves traffic. Those fail for completely different reasons, which is why both jobs exist. Note it reuses healthcheck.sh from Module 1, and that if: failure() dumps logs so a red build is diagnosable without re-running it.

Step 2 — add ruff config so lint is not noise

cat > ruff.toml <<'EOF'
line-length = 100
target-version = "py312"

[lint]
select = ["E", "F", "I", "UP", "B"]
EOF

pip install ruff
ruff check . && ruff format .

Step 3 — push and watch it fail, then pass

git switch -c ci/pipeline
git add .github ruff.toml
git commit -m "ci: add lint, test, build and smoke pipeline"
git push -u origin ci/pipeline

Open a Pull Request. Watch quality and test run in parallel; build is skipped because the ref is not main. Fix whatever ruff complains about, push again, and watch it go green.

Step 4 — make the checks binding

Settings → Branches → main → Edit. Enable Require status checks to pass before merging and select quality and test. Now merging red code is not possible, rather than merely discouraged.

Step 5 — merge and verify the artefact

# after merging the PR on GitHub:
git switch main && git pull

SHA=$(git rev-parse HEAD)
docker pull ghcr.io/<you>/urlshort:sha-$SHA
docker run --rm ghcr.io/<you>/urlshort:sha-$SHA python -c "import app.main; print('image ok')"

Step 6 — prove the gate works

git switch -c break/tests
sed -i 's/assert len(code) == 7/assert len(code) == 99/' tests/test_api.py
git commit -am "test: deliberately break a test"
git push -u origin break/tests

Open a PR. The merge button is now blocked. Revert the change, push, and watch it unblock. That transition is the entire point of the module.

Exercises

Exercise 1 — matrix builds

Run the test job against Python 3.11 and 3.12 simultaneously.

Solution 
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python: ["3.11", "3.12"]
    steps:
      - uses: actions/setup-python@v5
        with: { python-version: "${{ matrix.python }}" }

fail-fast: false matters: the default cancels all remaining matrix jobs on the first failure, which hides whether the problem is version-specific.

Exercise 2 — scheduled dependency scan

Scan the published image for CVEs every Monday at 06:00 UTC and fail on HIGH or CRITICAL.

Solution 
on:
  schedule:
    - cron: "0 6 * * 1"
  workflow_dispatch:

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: aquasecurity/trivy-action@0.24.0
        with:
          image-ref: ghcr.io/${{ github.repository }}:latest
          severity: "HIGH,CRITICAL"
          exit-code: "1"

This runs on a schedule rather than on push because new CVEs are published against code you have not touched. An image that was clean at build time is not clean forever.

Exercise 3 — a reusable composite action

Three jobs repeat checkout + setup-python + install. Factor that out.

Solution

.github/actions/setup/action.yml:

name: Setup Python env
runs:
  using: composite
  steps:
    - uses: actions/setup-python@v5
      with: { python-version: "3.12", cache: pip }
    - shell: bash
      run: pip install -r requirements.txt

Then in each job: - uses: ./.github/actions/setup (after checkout, since a local action must be on disk first).

Exercise 4 — read a pipeline critically

What is dangerous here?

on: [pull_request_target]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { ref: "${{ github.event.pull_request.head.sha }}" }
      - run: make deploy
        env: { AWS_KEY: "${{ secrets.AWS_KEY }}" }
Solution

pull_request_target runs with full repository secrets, and this workflow explicitly checks out the pull request's code. Anyone in the world can open a PR that changes the deploy target in the Makefile and have your CI run it with production credentials. It also deploys straight from an unreviewed PR with no gate. Use pull_request, deploy only from main, and scope the token.

Checkpoint

Job A installs dependencies; job B runs the tests and fails with "module not found". Why?
needs only orders jobs; it shares nothing. Either combine the steps into one job, or pass results explicitly via an artifact or a registry.
Why build the image once in CI and promote that same image through staging to production?
Base images move, transitive dependencies shift, timestamps change. A rebuild is a new artefact with new risk — so the thing you tested is not the thing you shipped.
Which is the most dangerous line in a workflow?
That combination runs untrusted code from any fork with your repository's secrets in scope — a full credential-exfiltration path from a single opened PR.
You should now be able to, without notes:
  • Distinguish continuous integration, delivery and deployment, and say what each demands of you.
  • Write a workflow with parallel jobs and correct needs ordering.
  • Start a service container and explain why localhost is right here but wrong in Compose.
  • Cache dependencies and Docker layers, keyed correctly.
  • Publish an image tagged with the commit SHA, and say why not latest.
  • Name three ways a pipeline leaks secrets and prevent each.
  • Make CI checks a blocking requirement on main.
  • Explain rolling vs blue/green vs canary and pick one for a given risk tolerance.
