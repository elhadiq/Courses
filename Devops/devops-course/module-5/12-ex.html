Exercise 1 — parameterise the whole stack

Add a redis_version variable and a terraform.tfvars.example file so a new engineer can bring the stack up without reading the code.

Solution 
# variables.tf
variable "redis_version" {
  type    = string
  default = "7-alpine"
}

# main.tf
resource "docker_image" "redis" {
  name = "redis:${var.redis_version}"
}
# terraform.tfvars.example  (commit THIS, not terraform.tfvars)
project       = "urlshort"
api_port      = 8000
api_image     = "ghcr.io/you/urlshort:sha-abc123"
redis_version = "7-alpine"

Exercise 2 — terraform in CI

Add a workflow that runs fmt -check, validate and plan on pull requests, but never apply.

Solution 
jobs:
  terraform:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: terraform } }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform fmt -check -recursive
      - run: terraform init -backend=false
      - run: terraform validate

-backend=false lets validation run without credentials or state access — safe on untrusted PRs. A real plan needs state and therefore credentials, which is precisely why it belongs behind an environment gate rather than on every fork's PR.

Exercise 3 — make a playbook idempotent

This task reports changed every run. Fix it two different ways.

- name: Install docker compose plugin
  ansible.builtin.shell: curl -fsSL https://example.com/install.sh | sh
Solution

Guard on an artefact:

- name: Install docker compose plugin
  ansible.builtin.shell: curl -fsSL https://example.com/install.sh | sh
  args:
    creates: /usr/local/lib/docker/cli-plugins/docker-compose

Or check first and act conditionally:

- name: Check for the plugin
  ansible.builtin.stat:
    path: /usr/local/lib/docker/cli-plugins/docker-compose
  register: compose_bin

- name: Install docker compose plugin
  ansible.builtin.shell: curl -fsSL https://example.com/install.sh | sh
  when: not compose_bin.stat.exists

Best of all: use the ansible.builtin.apt module with the official repository, so idempotency is the module's problem rather than yours.

Exercise 4 — adopt an unmanaged resource

Create a Docker volume by hand, then bring it under Terraform management without destroying it.

Solution 
docker volume create orphan-data

# add to main.tf:
# resource "docker_volume" "orphan" { name = "orphan-data" }

terraform import docker_volume.orphan orphan-data
terraform plan
# No changes — state now matches both the config and reality

This is the standard path for adopting infrastructure that predates your IaC adoption: write the resource block to match what exists, import, then confirm the plan is empty. A non-empty plan means your block does not yet describe reality accurately.
