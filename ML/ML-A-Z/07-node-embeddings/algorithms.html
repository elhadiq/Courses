PageRank by repeated averaging

Iterative method \(\cdot\) converges geometrically

Rank the nodes of a directed graph by importance, where being pointed at by an important node counts for more than being pointed at by an obscure one.

Input and output

Given. A directed graph and a damping factor \(\alpha\), conventionally 0.85.

Produce. A score for every node; the scores add to one.

The procedure, step by step

  1. Start with everything equal. Give every node the same score, one divided by the number of nodes.
  2. Let each node pass on its score. Every node splits its current score equally among the nodes it points to.
  3. Deal with nodes that point nowhere. A node with no outgoing links would absorb score and never release it. Collect the score held by all such nodes and redistribute it evenly over every node.
  4. Apply damping. Keep only the fraction \(\alpha\) of what was passed on, and distribute the remaining fraction evenly over all nodes. This models a surfer who occasionally jumps somewhere at random, and it is what stops small groups of mutually linking nodes from hoarding all the score.
  5. Repeat until settled. Fifty to a hundred rounds suffice for any graph, because the error shrinks by a factor of \(\alpha\) every round.

Why the answer is correct

Damping makes it possible to get from anywhere to anywhere, which guarantees that a single set of settled scores exists and that repeated averaging finds it regardless of the starting point.

Why it stops

Guaranteed: the distance to the answer is multiplied by \(\alpha\) each round.

What it costs

\(O(m)\) per round, so linear in the number of edges overall.

Where it goes wrong
  • Ignoring nodes with no outgoing links causes the scores to leak away and stop adding to one. This is the most common implementation bug.
  • Pushing \(\alpha\) towards 1 respects the link structure more but converges far more slowly and is easier to manipulate.
Worth knowing

Replacing the uniform random jump by a jump back to one chosen node gives personalised scores, which measure closeness to that node. This is the standard graph-based recommendation primitive.

Generating random walks

Sampling \(\cdot\) turns a graph into sequences

Produce sequences of nodes that can be treated like sentences, so that methods designed for text can be applied to a graph.

Input and output

Given. A graph, a walk length, and a number of walks to start from each node.

Produce. A collection of node sequences.

The procedure, step by step

  1. Choose a starting node. Work through every node in turn, so that none is neglected.
  2. Step to a random neighbour. Pick uniformly among the nodes joined to the current one.
  3. Continue to the required length. Typically 40 to 80 steps.
  4. Repeat from the same start. Ten walks per node is usual; different walks explore different directions.
  5. Read the sequences as sentences. Nodes appearing near one another in these sequences are treated as related, in the way that words appearing near one another in text are.
Why the answer is correct

On an undirected graph, a very long walk visits each node in proportion to how many edges it has — and nothing more. So a long walk tells you only the degree. All the information is in short walks, which is why the length is deliberately limited.

Why it stops

Fixed length, fixed count.

What it costs

Proportional to the total number of steps taken.

Where it goes wrong
  • Walks get trapped in dense regions and rarely cross weak bridges, so sparsely connected parts are under-represented.
  • Too long a walk washes out local structure, for the reason above.

The biased second-order walk

Sampling \(\cdot\) two knobs that change the meaning

Steer the walk so that it either stays near where it started or pushes away, and thereby choose what 'similar' will mean.

Input and output

Given. A graph and two numbers: \(p\) controlling return, \(q\) controlling outward movement.

Produce. Sequences whose statistics reflect the chosen bias.

The procedure, step by step

  1. Remember the previous node. Unlike an ordinary walk, this one looks back one step. That is what makes it second-order.
  2. Classify each candidate next node. From the current node, each neighbour is one of three things: the node just left; a node also joined to the one just left; or a node further away.
  3. Give each class a weight. Weight one divided by \(p\) for going back, one for staying at the same distance, one divided by \(q\) for moving outward.
  4. Normalise and step. Divide the weights by their total to get probabilities, and choose accordingly.
  5. Choose the knobs deliberately. Larger \(q\) keeps the walk local, so nodes playing similar structural roles look alike. Smaller \(q\) lets it roam, so nodes in the same region look alike. These are different notions of similarity and different tasks want different ones.

With \(q\) small most of the probability goes to nodes further out; with \(q\) large the walk stays in the neighbourhood it started in. One parameter, two entirely different notions of similarity.

Why the answer is correct

The walk is still memoryless once you regard the pair (previous, current) as the state, so the usual theory applies to that enlarged description.

Why it stops

Fixed length.

What it costs

Slightly more than an ordinary walk, since the neighbours of the previous node must be consulted. Precomputing these lookups costs memory proportional to the sum of squared degrees, which is prohibitive on graphs with very large hubs.

Where it goes wrong
  • Both knobs need choosing on held-out data. Their best values are task-dependent and not transferable between graphs.

Scoring candidate links

Scoring \(\cdot\) needs no training

Guess which pairs of currently unconnected nodes are likely to become connected.

Input and output

Given. A graph and a list of candidate pairs.

Produce. A score per pair; higher means likelier.

The procedure, step by step

  1. Count the shared neighbours. For a pair, the number of nodes joined to both. Two people with many mutual friends are likely to meet.
  2. Correct for popularity. Divide by the total number of distinct nodes joined to either. Otherwise two very well-connected nodes always score highly regardless of any real affinity.
  3. Weight rare neighbours more heavily. A shared neighbour joined to only three nodes is far more informative than one joined to ten thousand. Give each shared neighbour a weight falling off with how connected it is, and add these up.
  4. Rank. Sort the candidate pairs by score.
  5. Evaluate honestly. Remove the edges you intend to test before computing anything. Otherwise every method reads the answer off the graph it was given.

Why the answer is correct

These are heuristics with no optimality claim. Their justification is empirical — they remain hard to beat on many real networks.

Why it stops

Direct.

What it costs

Proportional to the product of the two nodes' degrees per pair.

Where it goes wrong
  • Choosing the negatives carelessly makes the numbers meaningless. There are vastly more non-edges than edges, and a randomly chosen non-edge is usually two nodes on opposite sides of the graph — trivially easy. Compare against hard negatives, such as pairs exactly two hops apart.
  • None of these scores can propose a link between two nodes with no shared neighbours at all, whatever the rest of the structure suggests.
