Scaling Ethereum

By the end of this lesson you will understand the scalability trilemma, how rollups move work off-chain, and the difference between optimistic and zero-knowledge rollups.

What you will be able to do

  • State the scalability trilemma and why Ethereum won't sacrifice decentralization.
  • Explain how a rollup executes off-chain (L2) and settles on L1.
  • Contrast optimistic rollups (fraud proofs) with ZK rollups (validity proofs).
  • Explain how batching amortizes the L1 cost across many transactions.

1. The scalability trilemma

Every permissionless blockchain wants three things: decentralization, security, and scalability. The trilemma, named by Vitalik Buterin, says improving one usually costs another. Ethereum keeps every node processing every transaction — great for decentralization and security, but a throughput bottleneck. You could raise throughput by making blocks bigger, but then only powerful machines could run a full node, pushing toward centralization. Some chains (like Solana) chose speed over decentralization; Ethereum refuses to compromise decentralization, which makes scaling genuinely hard.

2. Rollups: do the work off-chain

The leading answer is rollups. A rollup runs transactions on a dedicated layer 2 (L2), then posts compressed data (or a proof) back to layer 1 (L1). The heavy computation happens off-chain, so L1 avoids its throughput bottleneck while remaining the authoritative settlement layer. A rollup contract on L1 stores the L2 state (often a Merkle root) and accepts batches of transactions from a sequencer.

The power of a rollup is amortization: hundreds of L2 transactions are bundled into one L1 submission, so the fixed L1 cost is shared across all of them. The more transactions per batch, the lower the cost each one pays:

cost per tx = L1 cost ÷ number of transactions
1000 ÷ 100 = 10 each

Computing this amortized cost is one of the exercises. Rollups protect users through data availability (so anyone can reconstruct or exit) and state-transition integrity (proving the new state is valid).

3. Optimistic vs zero-knowledge rollups

The two dominant rollup types differ in how they prove the new state is correct:

 Optimistic rollupZK rollup
Proof typeFraud proofsValidity proofs (SNARKs/STARKs)
AssumptionAssume valid; anyone can challenge.Prove valid up front, verified on-chain.
WithdrawalWait a challenge window (~7 days).Near-instant.
ExamplesArbitrum, Optimism, BaseZKsync, Starknet, Scroll

An optimistic rollup posts state assuming it is correct, but leaves a challenge window (often about a week) in which anyone can submit a fraud proof; if upheld, the batch is reverted and the operator is slashed. A ZK rollup attaches a cryptographic validity proof to each state root, verified on-chain immediately — so there is no waiting period and withdrawals are fast, at the cost of expensive proof generation. Mapping a proof type to its rollup and its withdrawal wait are two of the exercises.

4. Maturity stages and beyond

Rollups mature through stages. Stage 0 still has heavy operator control (“training wheels”); stage 1 requires a working proof system and independent actors; stage 2 is truly decentralized with permissionless proofs and long user-exit windows. Other approaches — validiums, sidechains, danksharding, and stateless Ethereum with Verkle trees — push scaling further, but rollups are today's main strategy.
