Section 12 · Reading

Decentralized Applications

By the end of this lesson you will understand what makes an app a DApp, how its parts fit together, and how content-addressed storage (IPFS) and Merkle trees keep data verifiable without putting it all on-chain.

What you will be able to do

  • Define a DApp and contrast it with a traditional (legacy) application.
  • Identify the parts of the DApp stack: contracts, storage, and frontend.
  • Explain content addressing in IPFS and why it makes storage tamper-evident.
  • Describe how a Merkle root lets you verify off-chain data cheaply on-chain.

1. What is a DApp?

A DApp (decentralized application) flips the architecture of a normal app. A legacy app like Instagram has closed-source logic on a company's servers, a single central database, and one official frontend — if the company blocks you or shuts down, the app is gone.

A DApp has two goals: no single point of failure, and usable even if the whole team disappears. Its logic lives in smart contracts on Ethereum (usually open source), important data can live in those contracts, and users reach it through a frontend that anyone can replace. This buys a powerful property: censorship resistance. An official website can be blocked, but no one can stop an address from interacting with a public contract, and anyone can spin up an alternative frontend — as the Tornado Cash story showed, where the protocol stayed usable through IPFS gateways even after its website was taken down.

2. The DApp stack

Three layers make up a DApp. At minimum, a DApp needs the first and third:

LayerRole
Backend (smart contracts)The logic and value-bearing state, enforced trustlessly by the network. This is what makes it decentralized.
Data storageCritical data on-chain; everything else off-chain (indexers, IPFS) because on-chain storage is expensive.
Frontend (web UI)How users interact; easily replaceable by an alternative or community version.

So a genuine DApp needs at least a smart contract and a frontend. An app that keeps its core logic on a centralized server is really a hybrid, not a true DApp. Deciding whether something qualifies is the first exercise.

3. IPFS and content addressing

Storing everything on-chain is far too expensive, so DApps lean on decentralized off-chain storage. IPFS (the InterPlanetary File System) is a P2P storage network that is content-addressable: each file is hashed, and that hash is its address. You fetch a file by asking for its hash from any IPFS node.

This has a neat side effect: the address depends only on the content, so identical content always produces the same address, and any change to the content changes the address. That makes stored data tamper-evident — if a file's hash still matches, the file is exactly what it claimed to be. Computing such a content identifier (here using SHA-256 as a stand-in) is the second exercise.

4. Merkle trees: verify a lot with a little

Often a DApp needs to prove that some piece of data belongs to a large set — for example, that an address is on an NFT allowlist — without storing the whole set on-chain. The trick is a Merkle tree: hash all the leaves, then repeatedly hash pairs together up the tree until a single Merkle root remains. Only that one root is stored on-chain.

leaves → hash pairs → hash pairs → … → single root

Because the root is a fingerprint of the whole set, anyone can later prove an item is included by supplying a short path of sibling hashes — the contract recomputes the root and checks it matches. You store one 32-byte value instead of thousands, yet keep on-chain verification. Building a Merkle root from a list of leaves is the capstone exercise.

Check your understanding

  1. What two components does a DApp need at minimum? (Answer: a smart contract and a frontend.)
  2. Why does identical content get the same IPFS address? (Answer: the address is the hash of the content.)
  3. What single value does a Merkle tree store on-chain? (Answer: the Merkle root.)
  4. Why not store all DApp data on-chain? (Answer: on-chain storage is expensive and does not scale.)
