Digital Signatures

A signature is how you prove “I authorize this” without revealing your secret key. This section explains what a signature proves, how signing and verifying work, and two subtle rules that keep Bitcoin safe.

What you will be able to do

  • State the three things a digital signature guarantees.
  • Explain signing and verifying in terms of the key pair from Section 4.
  • Say why the random number used when signing must never repeat.
  • Read SIGHASH flags — which parts of a transaction a signature covers.
  • Understand the low-S rule and why it exists.

1. What a signature proves

When Alice signs a transaction, the signature simultaneously guarantees three things to everyone on the network:

  • Authentication — the signature could only have been made by the holder of the private key. It really is Alice.
  • Integrity — the exact transaction Alice signed cannot be altered afterward; change one byte and the signature no longer verifies.
  • Non-repudiation — Alice cannot later deny she authorized it; only her key could have produced the signature.

Crucially, all of this happens without Alice revealing her private key. She proves she knows the secret without showing it.

2. Signing and verifying

Recall the key pair from Section 4. Signing uses the private key; verifying uses the matching public key. The signer feeds the message (a digest of the transaction) plus their private key into a signing algorithm, producing a signature. Anyone can then feed the message, the signature, and the public key into a verify algorithm that answers only true or false.

Bitcoin has used two signing schemes. The original is ECDSA. Since the 2021 Taproot upgrade it also supports Schnorr signatures, which are simpler, provably secure, and enable neat tricks like combining several signatures into one. Both rely on the same secp256k1 curve from Section 4.

3. The danger of reused randomness

Signing requires a fresh random number (called a nonce) each time. This is not a minor detail: if the same nonce is ever used to sign two different messages, anyone can do simple algebra on the two signatures and recover the private key. Real wallets have lost funds to this exact bug. Modern schemes derive the nonce deterministically from the key and message to make reuse impossible.

Takeaway. A signature scheme is only as safe as its randomness. Never roll your own signing code — use a vetted library.

4. What does the signature actually sign? SIGHASH flags

A signature commits to a specific view of the transaction. A one-byte SIGHASH flag appended to each signature says which parts are covered. The base types:

FlagValueCommits to…
SIGHASH_ALL0x01All inputs and all outputs (the normal case).
SIGHASH_NONE0x02All inputs, but no outputs.
SIGHASH_SINGLE0x03All inputs and only the matching output.
ANYONECANPAY0x80A modifier (add to the above): commit to only this input.

The modifier bit 0x80 is combined with a base type. So 0x81 means SIGHASH_ALL + ANYONECANPAY. To decode a flag byte: the low bits (flag & 0x1f) give the base type, and the 0x80 bit tells you whether ANYONECANPAY is set.

5. Signature encoding and the low-S rule

An ECDSA signature is a pair of numbers, (r, s), packaged in a format called DER. A DER signature starts with the byte 0x30, then a length, then each of r and s preceded by a 0x02 tag and its own length.

There is a subtlety: for any valid signature (r, s), the pair (r, n−s) is also mathematically valid, where n is the curve order. An attacker could flip one into the other, changing the transaction's id without invalidating it — a problem called malleability. Bitcoin fixes this with the low-S rule: only signatures whose s value is in the lower half of the range (s ≤ n/2) are accepted.
