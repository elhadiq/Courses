The Ethereum Virtual Machine

By the end of this lesson you will understand the EVM as a stack machine, know its four data areas, and see how gas meters every opcode to make it quasi-Turing-complete.

What you will be able to do

  • Describe the EVM as a stack-based virtual machine running bytecode.
  • Distinguish its four data areas: stack, memory, storage, and calldata.
  • Trace a tiny bytecode computation on the stack.
  • Explain how gas is charged per opcode and why that makes the EVM quasi-Turing-complete.

1. A stack machine

The EVM is the “CPU” of the world computer. It runs low-level instructions called bytecode, and it is a stack machine: instead of named registers, it works on a stack — a last-in, first-out pile of values. Each stack item is a 32-byte word, and the stack can hold at most 1,024 items.

Most opcodes take their operands from the top of the stack and push their result back. For example, ADD pops the top two values and pushes their sum. Building a short computation on the stack is the first exercise.

push 2, push 3, ADD → stack top = 5
push 2, push 3, MUL, push 4, ADD → 2×3=6, 6+4 = 10

2. The four data areas

Where a contract keeps data matters enormously — for both behaviour and gas cost. The EVM has four distinct areas:

AreaNatureLives for
StackLIFO, 32-byte words, max 1024.The current computation.
MemoryByte-addressable scratch space, starts at 0.One execution (volatile).
StorageKey⇒value slots (32 bytes each).Forever — the contract's persistent state.
CalldataImmutable input to the call.Read-only, the call's input.

The key distinction is persistence: only storage survives between transactions, which is why writing to it is by far the most expensive. Memory and the stack vanish when execution ends, and calldata is fixed input you can only read. Deciding whether a location is persistent is the third exercise.

3. Gas and quasi-Turing completeness

The EVM can run any program (it is Turing complete), but the halting problem means it cannot know in advance whether a program will stop. The fix is gas: every opcode has a fixed gas cost, and before each step the EVM checks there is enough gas left. Run out, and execution halts and reverts. This makes the EVM quasi-Turing-complete: it runs anything, but only within a bounded amount of computation.

Costs reflect how demanding an operation is. A few from the Yellow Paper:

OperationGas
Add two numbers (ADD)3
Multiply (MUL)5
Keccak-256 hash (base)30
Send a transaction (base)21,000

At the end, the validator is paid gas used × gas price, and any unused gas is refunded. If it runs out mid-way, the state rolls back but the gas is still charged — the validator did the work. Summing the gas of a sequence of opcodes is the second exercise.

Check your understanding

  1. What order does the EVM stack follow? (Answer: last-in, first-out.)
  2. Which data area survives between transactions? (Answer: storage.)
  3. What happens if a transaction runs out of gas? (Answer: it halts and reverts, but gas is still charged.)
  4. Why is the EVM only quasi-Turing-complete? (Answer: computation is bounded by gas.)
