Ethereum Nodes

By the end of this lesson you will know what a node is, why Ethereum needs two clients, when to run a full node, and how to talk to a node through the JSON-RPC interface.

What you will be able to do

  • Explain what an Ethereum node does and why the network needs many of them.
  • Describe the split between an execution client and a consensus client.
  • Weigh the trade-offs between a full node, a public testnet, and a local simulation.
  • Read a JSON-RPC request and response, and convert a hex result into a decimal number.

1. What is a node?

A node is a computer running Ethereum client software that connects to the peer-to-peer network. The health, resilience, and censorship resistance of the whole network depend on having many independently operated, geographically spread nodes. A full node downloads the entire blockchain and keeps its data, so it can verify every transaction and contract for itself and help new nodes get started. An archive node goes further and keeps every historical state forever.

Since The Merge, an Ethereum node is actually made of two cooperating clients:

ClientJobExamples
Execution clientRuns transactions and smart contracts (the EVM), keeps the state.Geth, Nethermind, Besu, Erigon, Reth
Consensus clientRuns proof of stake: agreeing on which blocks are canonical.Lighthouse, Lodestar, Nimbus, Prysm, Teku

You can mix and match: the book uses the Geth–Prysm and Reth–Lighthouse pairings as examples, but any execution client can pair with any consensus client.

2. Should I run a full node?

Running your own full node gives you an authoritative, trustless view of the chain — you verify everything yourself instead of trusting someone else's server. The cost is hardware, bandwidth, and time. There are three broad options depending on what you are doing:

OptionGood forCost
Full node (mainnet)Maximum trust and independence; supporting the network.High storage and bandwidth.
Public testnetTesting DApps against a realistic shared network with free test ether.Moderate.
Local simulationFast, private development and unit tests.Very low; not the real network.

The first time a client connects, it must synchronize. A full sync validates every block from genesis and can take days. Most clients instead offer a fast sync (snap sync for execution clients, checkpoint sync for consensus clients) that skips full validation until it reaches the tip of the chain, then resumes full validation from there.

3. Talking to a node: JSON-RPC

Clients expose an API whose commands are encoded as JSON — the JSON-RPC interface. It is your program's gateway into Ethereum. It is normally served over HTTP on port 8545, restricted by default to connections from your own machine (localhost, 127.0.0.1) for safety.

Every request has four fields: jsonrpc (always exactly "2.0"), method (the command name), params (its arguments), and id (a number you choose so you can match the reply). For example, asking a Geth node its version:

request  {"jsonrpc":"2.0","method":"web3_clientVersion","params":[],"id":1}
response {"jsonrpc":"2.0","id":1,"result":"Geth/1.14.3-stable/..."}

Numbers come back hex-encoded. When you ask for the gas price you might get "0x1B1717FC7". To make sense of that you convert the hexadecimal string to a decimal integer:

0x1B1717FC7 → 7,271,972,807 wei → ≈ 7.27 gwei

In real programs you would use a library such as web3.py or ethers.js rather than raw HTTP, but the underlying protocol is exactly this. Converting hex results and reading JSON responses are the skills the exercises drill.

Check your understanding

  1. What two clients make up an Ethereum node today? (Answer: an execution client and a consensus client.)
  2. On which port is JSON-RPC usually served? (Answer: 8545.)
  3. What decimal value does 0x10 represent? (Answer: 16.)
