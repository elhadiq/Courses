Section 11 · Reading

Oracles

By the end of this lesson you will understand why the EVM cannot fetch real-world data or true randomness on its own, and how oracles bridge that gap through three design patterns.

What you will be able to do

  • Explain why determinism forbids on-chain randomness and external data.
  • Describe what an oracle is and what functions every oracle performs.
  • Compare the immediate-read, publish-subscribe, and request-response patterns.
  • Explain how decentralized oracles resist manipulation by aggregating sources.

1. Why oracles are needed

The EVM must be perfectly deterministic: every node running the same contract on the same state has to reach exactly the same result, or the network could never agree on the state. Two consequences follow. First, there can be no true randomness on-chain — if a contract called a real random function, node A might store 3 and node B might store 7, and consensus would collapse. Second, real-world data cannot appear by itself; the only way external information enters is inside the data field of a signed transaction.

But data placed in a transaction is only as trustworthy as whoever put it there. An oracle is the mechanism that bridges the off-chain world to smart contracts — ideally in a trustless or near-trustless way — supplying things like asset prices, sports results, weather, or verifiable random numbers. The catch is that a bad oracle becomes a target: if a “smart will” releases a fortune when an oracle says someone has died, attackers have every incentive to corrupt that oracle.

2. What every oracle does

By definition, an oracle performs three jobs: it collects data from an off-chain source, transfers it on-chain in a signed message, and makes it available so that other contracts can read it (through a retrieve-style call) or clients can read it directly.

3. Three design patterns

There are three main ways to arrange an oracle, each suited to a different kind of data:

PatternBest forHow it works
Immediate-readOne-off lookups (“is this person over 18?”).Data is stored once in the oracle contract; anyone reads it just-in-time.
Publish-subscribeData that changes often (price feeds, weather).The oracle updates a value and flags it; subscribers poll or listen for changes.
Request-responseDatasets too big to store on-chain.A contract emits a request event; off-chain infrastructure fetches, signs, and returns just the needed slice.

Choosing between them is a trade-off: a slowly changing interest rate fits publish-subscribe (read the stored value when needed), while a huge market dataset queried in small pieces suits request-response. Matching a need to its pattern is the first exercise.

4. Trust, authentication, and decentralization

Because the oracle and the transport may be run by different parties, data could be tampered with in transit. Two approaches restore trust: authenticity proofs (cryptographic signatures or zero-knowledge attestations proving the data came unaltered from the right source) and trusted execution environments (secure hardware that vouches for the computation).

The strongest answer is a decentralized oracle: instead of one provider, many independent nodes each report a value, and the contract combines them — commonly by taking the median. One corrupted or faulty node cannot move a median much, so aggregation makes the feed far harder to manipulate. Computing that median is the third exercise; deciding whether a given piece of data even needs an oracle is the second.

Check your understanding

  1. Why can't the EVM generate a true random number? (Answer: it would break determinism and consensus.)
  2. Which pattern suits a frequently changing price feed? (Answer: publish-subscribe.)
  3. How do decentralized oracles resist a bad data point? (Answer: aggregate many sources, e.g. by median.)
  4. Does a Keccak-256 hash of on-chain data need an oracle? (Answer: no — it is deterministic and computable on-chain.)
