Smart Contracts and Solidity

By the end of this lesson you will know what a smart contract really is, how its life cycle works, the core Solidity data types, and why transactions are atomic.

What you will be able to do

  • Define a smart contract as immutable, deterministic EVM code.
  • Trace a contract's life cycle from source, to bytecode, to a deployed address.
  • Recognise Solidity's basic data types and integer sizes.
  • Explain transaction atomicity: all changes commit, or all roll back.

1. What a smart contract is

The name is a bit misleading: an Ethereum smart contract is neither smart nor a legal contract. It is simply an immutable computer program that runs deterministically inside the EVM. Four words unpack that definition. It is a computer program (the word “contract” has no legal meaning here). It is immutable: once deployed, the code cannot be changed — the only way to “update” it is to deploy a new one. It is deterministic: the result is the same for everyone, given the same transaction and blockchain state. And it runs in a limited EVM context, able to see only its own state, the calling transaction, and recent block information.

2. Life cycle of a contract

A contract is written in a high-level language such as Solidity, then compiled to EVM bytecode so it can run. It is placed on chain by a special contract-creation transaction whose to field is empty. Its address is computed from the creator's account and nonce. Crucially, a contract account has no private key — we say contracts “own themselves.”

From then on, a contract only runs when a transaction calls it. Contracts never act on their own or in the background; every execution ultimately traces back to a transaction from an EOA. A contract can call another contract, which can call another, but an EOA always starts the chain, and the world computer runs one thread at a time.

3. Solidity data types

Solidity is a statically typed language. A handful of core types cover most contracts:

TypeMeaning
booltrue or false.
int / uintSigned / unsigned integers, in 8-bit steps from 8 to 256 bits. Bare uint means uint256, matching the EVM word.
addressA 20-byte account, with members like .balance and .transfer.
bytes / stringFixed (bytes1…bytes32) or dynamic byte arrays.
enum, struct, mappingUser-defined labels, grouped fields, and key⇒value lookup tables.

Solidity also has handy unit suffixes. The ether and wei suffixes make code readable: instead of require(withdrawAmount <= 100000000000000000) you write require(withdrawAmount <= 0.1 ether). An unsigned integer of N bits holds values from 0 up to 2N−1 — so a uint8 maxes out at 255. Computing these limits, and checking which bit-widths are valid, are among the exercises.

4. Atomic execution

Transactions are atomic: they run in full or not at all, no matter how many contracts they touch. If execution reaches the end successfully, every state change is committed together. If it fails at any point — an error, or a failed require check — all of its effects are rolled back as if it never ran. The attempt is still recorded and the gas spent is still charged, but no contract or account state changes. This all-or-nothing behaviour is what keeps contracts safe from ending up in half-finished states, and it is exactly what the third exercise models.

Check your understanding

  1. Can a deployed contract's code be edited? (Answer: no — you must deploy a new one.)
  2. What starts every contract execution? (Answer: a transaction from an EOA.)
  3. What is the maximum value of a uint8? (Answer: 255.)
  4. If a transaction fails halfway, what happens to its changes? (Answer: all rolled back.)

Practice. Three Python exercises: (1) compute the maximum value of a uintN, (2) decide whether a given bit-width is a valid Solidity unsigned-integer size, and (3) simulate atomic execution, committing a list of operations or reverting if any one fails.
