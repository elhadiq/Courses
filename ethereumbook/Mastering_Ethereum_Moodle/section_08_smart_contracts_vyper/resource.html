Section 8 · Reading

Smart Contracts and Vyper

By the end of this lesson you will understand Vyper's security-first philosophy, what it deliberately leaves out, its function decorators, and its built-in overflow protection.

What you will be able to do

  • Explain why Vyper omits features like modifiers, inheritance, and overloading.
  • List the main function decorators and the rules that constrain them.
  • Describe Vyper's explicit, bounds-checked type conversions.
  • Explain built-in overflow protection and why it matters.

1. Why Vyper exists

In 2023 alone, nearly $2 billion was stolen through smart-contract vulnerabilities. Most bugs are honest mistakes, but the loss is real. Vyper is a contract language for the EVM, inspired by Python, whose central goal is auditability: it tries to make misleading or unsafe code virtually impossible to write. Its strategy is subtraction — it deliberately leaves out powerful Solidity features that make code harder to reason about.

Feature Vyper omitsWhy
ModifiersThey can silently change state; use explicit inline checks instead.
InheritanceForces readers to jump between files; multiple inheritance is confusing.
Inline assemblyBreaks the ability to search for where a variable is used.
Function overloadingTwo functions with the same name is ambiguous.

The modifier case is the clearest. A Solidity modifier can look like a harmless precheck yet secretly call another function that advances the contract's state — a new developer calling the function might never notice. Vyper removes modifiers entirely: if you are checking a condition, write an inline assert; if you are changing state, make that change explicit in the function body.

2. Decorators

Each Vyper function begins with a decorator that declares what it may do. Understanding them is central to reading Vyper:

DecoratorMeaning
@externalCallable from outside the contract.
@internalCallable only from inside (the default).
@viewMay read but not change state.
@pureMay not read state at all.
@payableMay receive ether.
@nonreentrantLocks the function against reentrancy attacks.

Vyper enforces the logic of these decorators. Every function must be marked exactly one of @external or @internal — never both, never neither. And a function cannot be both @payable and @view, because receiving value is a state change and so contradicts “view.” The compiler rejects any program that breaks these rules. Checking a decorator combination for validity is one of the exercises.

3. Explicit, safe type conversion

Where Solidity often converts types implicitly, Vyper requires every conversion to be written out with convert(), and it always bounds-checks. Converting a small type up to a bigger one is safe; converting a big type down to a smaller one will revert the transaction if the value does not fit. There is no silent truncation — every conversion is intentional and range-checked.

small_value: uint8 = 42
large_value: uint256 = convert(small_value, uint256)  # safe upcast
back_to_small: uint8 = convert(large_value, uint8)   # bounds-checked

4. Overflow protection built in

Integer overflow has caused catastrophic bugs — a 2018 flaw in an ERC-20 token let an attacker mint an astronomically large balance. Vyper has always shipped built-in overflow protection: addition, subtraction, multiplication, and division throw an exception on overflow or underflow, and clamps enforce bounds whenever a value is loaded, passed, or assigned. So safe_add(a, b) on 8-bit integers succeeds when the sum fits in 0–255 but reverts when it would exceed 255. (Modern Solidity 0.8+ added similar checks, but Vyper was designed this way from the start.)

Contracts write data to two places: the global state (a contract's own persistent storage, which it cannot share with other contracts) and logs (searchable events, with up to four indexed arguments). Modelling the safe-add rule and the convert bounds-check are the remaining exercises.

Check your understanding

  1. Why did Vyper remove modifiers? (Answer: they can hide state changes and hurt auditability.)
  2. Which two decorators can never appear together? (Answer: @payable and @view.)
  3. What does Vyper do on a downcast that does not fit? (Answer: it reverts.)
  4. What happens when 200 + 100 overflows a uint8? (Answer: it reverts / throws.)

Practice. Three Python exercises: (1) a SafeMath-style safe_add that reverts on overflow, (2) a bounds-checked convert that reverts when a value is out of range, and (3) a validator for a function's decorator set, enforcing Vyper's external/internal and payable/view rules.
