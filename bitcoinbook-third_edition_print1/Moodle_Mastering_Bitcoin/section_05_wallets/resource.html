Section 5 · Reading

Wallets

A wallet does not hold coins — it holds keys. This section explains how modern wallets grow an entire tree of keys from a single backup phrase, and how those keys are organized.

What you will be able to do

  • Explain what a wallet really stores (keys, not coins).
  • Contrast old “bag of keys” wallets with modern seed-based (HD) wallets.
  • Read a BIP39 recovery phrase and relate entropy to word count.
  • Parse a BIP32 derivation path such as m/84'/0'/0'/0/0.
  • Recognize hardened derivation and why it matters.

1. A wallet holds keys, not coins

This trips up almost every beginner, so let us be blunt: your coins are never “in” your wallet. The coins (UTXOs, Section 2) live on the shared ledger that every node keeps. Your wallet app simply stores the private keys (Section 4) that can unlock them, and uses those keys to build and sign transactions. Lose the keys, lose access to the coins — even though the coins still sit on the ledger, unreachable.

2. The old way: a bag of unrelated keys

The earliest wallets just generated a fresh random private key whenever you needed one and stored them all in a file. These are called nondeterministic wallets — “non-deterministic” because the keys have no relationship to each other; each is independent randomness.

The problem is backup. Every new key is new randomness, so you must back up the file again and again. Miss one key and the coins it holds are lost. This fragility is exactly what the modern design fixes.

3. The modern way: one seed grows a whole tree

Today's wallets are Hierarchical Deterministic (HD) wallets, defined by a standard called BIP32. “Deterministic” means every key is computed from one starting secret — the seed — using a repeatable formula. Same seed, same keys, every time. So you back up the seed once and you have backed up every key you will ever use, past and future.

“Hierarchical” means the keys are organized as a tree: the seed produces a master key, which produces child keys, which produce grandchildren, and so on. This lets a wallet keep separate branches for different accounts or purposes.

4. The recovery phrase (BIP39)

A raw seed is a long unreadable number — easy to copy wrong. So BIP39 encodes it as a list of ordinary words drawn from a fixed 2048-word list: the recovery phrase (or mnemonic, or seed phrase) you have surely seen wallets ask you to write down.

How many words? It depends on how much randomness (entropy) the wallet uses. The scheme appends a small checksum of ENT / 32 bits, then splits the total into 11-bit chunks — one word per chunk. So the count follows a simple formula:

words = (ENT + ENT/32) / 11

128 bits → 12 words  ·  160 → 15  ·  192 → 18  ·  224 → 21  ·  256 bits → 24 words

Security note. Anyone who reads your recovery phrase controls all your coins. Write it on paper, never a photo or cloud note, and store it physically. This is the single most important habit in all of Bitcoin custody (Section 13).

5. Addressing keys in the tree: BIP32 paths

Because keys form a tree, we need a way to name a position in it. That is a derivation path, written like a file path:

m / 84' / 0' / 0' / 0 / 0
|    |    |    |   |   |
|    |    |    |   |   ↳ address index (5th)
|    |    |    |   ↳ change (0=receive, 1=change)
|    |    |    ↳ account number
|    |    ↳ coin type (0 = Bitcoin)
|    ↳ purpose (84 = native SegWit)
↳ m = master key (the root)

Each step down the tree is one number. Reading a path just means splitting on /, dropping the leading m, and turning each level into its number. The apostrophe on some levels signals something important, covered next.

6. Hardened derivation

An apostrophe (') — or the letter h — marks a level as hardened. Concretely, a hardened level adds 231 (2,147,483,648) to its index. So 0' is really child number 2147483648, and 44' is 2147483692.

Why bother? Normal (non-hardened) derivation has a convenient-but-dangerous property: if someone gets one child private key and also has the parent public key, they can compute the parent private key and every sibling. Hardened derivation deliberately breaks that shortcut — it leaves the parent public key out of the math — so a leaked child key stays contained. That is why account-level nodes are always hardened.

child is hardened ⇔ child_number ≥ 231 (2147483648)
